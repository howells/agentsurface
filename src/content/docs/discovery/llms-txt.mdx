## Summary

llms.txt is a proposal (not a standard), now at v2 (updated 2026-08-10), for a file served at /llms.txt that publishes a curated, token-efficient index of your site. Rather than agents crawling your entire documentation, llms.txt lets you declare upfront what matters most. The confirmed consumers are narrow: IDE and coding-agent workflows - Cursor, Claude Code, and similar tools - that index the file during project setup or on demand. Whether other tools read it depends on the tool, and Google says no special AI text files are needed; see [Adoption and Consumption](#adoption-and-consumption) below.

- Served at /llms.txt as text/plain; charset=utf-8
- Required: H1 with product/site name
- Recommended: blockquote summary, H2 sections with links and descriptions
- Link format: `- [Title](url): description`
- Total size under 5,000 tokens is this site's guideline; the proposal sets no cap
- Use ## Optional section for lower-priority content
- Worth shipping for documentation and developer-tool sites; not a general-site AEO tactic

The `llms.txt` proposal, put forward by Jeremy Howard in September 2024 at [llmstxt.org](https://llmstxt.org), suggests a standard location to publish a curated, token-efficient index of their content. Where a sitemap describes every URL for crawlers, `llms.txt` describes the most important content for AI agents - with enough context to navigate without crawling the full site.

## The Problem It Solves

An AI agent trying to use your API or understand your product faces a practical constraint: context windows are finite. Crawling your entire documentation site could cost hundreds of thousands of tokens before the agent answers a single question. `llms.txt` moves the curation work to the publisher, letting you declare in advance what an AI needs to know and where to find it.

The confirmed value is narrow but real: IDE and coding-agent workflows - Cursor, Claude Code, and similar tools - fetch `llms.txt` on demand when indexing a documentation or developer-tool site during project setup. That is the use case this page's guidance is written for.

## Canonical Format

`llms.txt` is served at the root path (`/llms.txt`) as `text/plain; charset=utf-8`. The format is a subset of Markdown with a specific structure:

```markdown
# Product Name

> One-paragraph summary of what this product is and who it's for.

## Section Name

- [Page Title](https://example.com/page.md): Short description of what this page covers.
- [Page Title](https://example.com/other.md): Short description.

## Another Section

- [Page Title](https://example.com/more.md): Short description.

## Optional

- [Less Critical Page](https://example.com/optional.md): Lower-priority content.
```

The only required element is the H1 (`#`) with the product or site name. Everything else is recommended but optional.

**H1** - Required. Site or product name. One per file.

**Blockquote summary** - Recommended. One paragraph describing the product and its intended users. Appears directly below the H1.

**H2 sections** - Group related links. Section names are free-form.

**Link list items** - Each item is `[Title](URL): Description`. The colon-and-description suffix is optional but strongly recommended. Descriptions help agents prioritize which links to fetch.

**`## Optional` section** - A specially named section that agents can skip when operating under context pressure. Put supplementary content - changelog entries, older tutorials, edge-case reference - in this section.

## The .md URL Convention

Links in `llms.txt` should point to the Markdown version of each page, not the HTML version. llms.txt v2 allows two forms: `.md` appended to the full page URL (`page.html.md`), or the extension replaced (`page.md`), because some publishing tools replace it. Pick one and use it consistently:

```
https://docs.example.com/authentication       → HTML page for browsers
https://docs.example.com/authentication.md    → Markdown for agents
```

v2 also names the link relations for discovery from a page: `rel="alternate" type="text/markdown"` points to the page's Markdown version, and `rel="describedby"` points to the `llms.txt` file that covers it. Provide them as HTML `<link>` elements or an HTTP `Link:` header ([v2 changes](https://llmstxt.org/changes.html)).

If your site does not yet serve `.md` endpoints, link to the HTML pages as a fallback. See [Content Negotiation](./content-negotiation) for how to implement Markdown serving.

## Token Budget

As a house guideline, keep the full `llms.txt` under 5,000 tokens (the proposal itself sets no cap). That fits comfortably in a single context window turn and lets agents load the entire index at once without truncation.

Published files vary enormously in size. A large vendor's index can run to thousands of tokens and its `llms-full.txt` to hundreds of thousands, and those counts change whenever the docs do. Count your own files with your own tokenizer and date the measurement. The index should be the compact version - agents fetch the full content when they need depth.

## Real Examples

**Anthropic** publishes two files:

- `/llms.txt` - an index with sections for Claude models, APIs, and product features
- `/llms-full.txt` - a much larger file with all documentation content inlined

**Stripe** publishes three files across their domains:

- `stripe.com/llms.txt` - product overview and marketing content
- `docs.stripe.com/llms.txt` - full API and integration documentation
- `support.stripe.com/llms.txt` - help center and troubleshooting content

Stripe also uses an `## Instructions` section (see below) to give behavioral guidance to AI agents about how to handle Stripe-specific concepts.

**Vercel** organizes sections by product area:

- Deployment, Edge Functions, Storage, Observability, and CLI each appear as separate H2 sections
- Each link includes a description that differentiates it from adjacent pages
- The index stays compact despite covering dozens of products

## The Instructions Section

Stripe's pattern of adding an `## Instructions` section is worth adopting. Unlike a pure index, this section gives behavioral guidance to AI agents:

```markdown
## Instructions

- When discussing pricing, always refer users to the current pricing page rather than quoting figures directly.
- The API uses camelCase for JSON keys in requests and snake_case in webhook payloads - these are not inconsistencies.
- Authentication is always via Bearer token in the Authorization header, never via query parameters.
- Rate limit errors use HTTP 429 with a Retry-After header. Always surface this to the user.
```

Agents that read this section have the directives in context when answering; treat it as steering, not enforcement. This is particularly useful for:

- Correcting common misconceptions agents develop from training data
- Flagging which information goes stale quickly (pricing, feature availability)
- Clarifying naming conventions and terminology that conflict with common usage
- Directing agents to authoritative sources for specific topics

## llms-full.txt

`llms-full.txt` is the companion to `llms.txt`. Where the index links to pages, the full file inlines all content:

```markdown
# Product Name

> Summary of the product.

## Authentication

### API Keys

[Full content of the authentication page...]

### OAuth 2.0

[Full content of the OAuth page...]
```

`llms-full.txt` serves two distinct use cases:

**RAG pipelines** - Teams building internal knowledge bases chunk and embed `llms-full.txt` rather than crawling and parsing HTML. A single well-structured file is easier to process than hundreds of HTML pages.

**Optional material for tools and users** - `llms-full.txt` is publisher-provided material that a user or a tool can fetch, for example to paste into a chat or load as a documentation source. What a given tool does with it, and whether it keeps a local copy, is tool-specific; check that tool's documentation rather than assuming it.

Maintain `llms-full.txt` as a generated artifact. Inlining content manually does not scale. See [Generation Tools](#generation-tools) below.

## Serving Requirements

Serve both files as `text/plain; charset=utf-8`. That is a site convention, not a requirement of the proposal, which describes a Markdown document and does not forbid `text/markdown`. What matters is that you never serve an HTML shell (a rendered page, a login redirect or a single-page-app wrapper) at these paths, because a client expects the file's text.

```
Content-Type: text/plain; charset=utf-8
Cache-Control: public, max-age=86400
```

A 24-hour cache is appropriate since `llms.txt` changes infrequently. If your documentation deploys frequently, use a shorter TTL or add a `Last-Modified` header so agents can revalidate efficiently.

## What Lighthouse Checks

Lighthouse's `llms-txt` audit verifies the file is actually usable, not just present ([source](https://github.com/GoogleChrome/lighthouse/blob/main/core/audits/agentic/llms-txt.js)):

- The file must be fetchable. A failed fetch or a 5xx response fails the audit outright; a 4xx response marks it not applicable.
- The content must include a Markdown H1 (`# Title`).
- The content must include at least one Markdown link.
- The content must be at least 50 characters long.

These map directly onto the canonical format above: the required H1, and a link list with real entries rather than a placeholder file.

See [Referencing llms.txt from robots.txt](/docs/discovery/robots-txt#referencing-llmstxt-from-robotstxt) for the comment-line convention some crawlers recognize.

## Generation Tools

Most documentation platforms now generate `llms.txt` automatically:

**Mintlify** - generates `llms.txt` and `llms-full.txt` from your docs config. No additional configuration required.

**Fern** - generates `llms.txt` alongside OpenAPI documentation. Configurable section grouping.

**GitBook** - generates `llms.txt` from your space's table of contents.

**Docusaurus** - community plugin `docusaurus-plugin-llms-txt` generates both files at build time.

**WordPress** - plugins available for major documentation themes.

**Next.js** - implement as a route handler:

```typescript
// app/llms.txt/route.ts
import { source } from "@/lib/source";

export async function GET() {
  const pages = source.getPages();

  const sections = groupPagesBySection(pages);

  const lines = ["# Your Product Name", "", "> What your product does and who it serves.", ""];

  for (const [section, sectionPages] of Object.entries(sections)) {
    lines.push(`## ${section}`, "");
    for (const page of sectionPages) {
      lines.push(`- [${page.data.title}](${page.url}.md): ${page.data.description}`);
    }
    lines.push("");
  }

  return new Response(lines.join("\n"), {
    headers: {
      "Content-Type": "text/plain; charset=utf-8",
      "Cache-Control": "public, max-age=86400",
    },
  });
}
```

## Directories

If you want to verify your file is discoverable:

- **llmstxthub.com** - directory of submitted `llms.txt` files with category browsing
- **llms-txt-hub** - GitHub-based registry with programmatic access
- **llms-txt.io** - validation tool that checks format and token count

Submission to directories is optional. The primary value of `llms.txt` comes from agents discovering the file at the standard path, not from directory listings.

## Adoption and Consumption

Consumption is tool-dependent, and the evidence that general-purpose crawlers and inference-time browsing use `llms.txt` is thin:

- The documented purposes of the major AI crawlers - GPTBot, ClaudeBot, PerplexityBot - do not include fetching `llms.txt`. That is not proof they never request it.
- Google's guidance says no special AI text files are needed to appear in its AI features.
- Google's John Mueller compared `llms.txt` to the keywords meta tag, and Google's own AI-optimization guidance states that files like this are not needed or used for its systems.

So `llms.txt` is not an answer-engine-optimization (AEO) strategy for a general site. Treat any claim that it improves visibility in AI Overviews or chatbot answers with skepticism.

The genuine, confirmed value is narrow: coding agents and IDE assistants - Cursor, Claude Code, and similar tools - fetch `llms.txt` on demand when indexing a documentation or developer-tool site. That on-demand consumption during a developer's task is real, and it is the reason this site still ships an `llms.txt`.

**Recommendation:** worth shipping for documentation and developer-tool sites - it is cheap to generate and there is real coding-agent consumption. Do not ship it expecting an AEO benefit on a general marketing or content site; there is no evidence it changes how answer engines see you.

## Modular, per-section indexes

For a large site, publish section-level `llms.txt` files alongside the root index - `/docs/llms.txt` for documentation, `/api/llms.txt` for API reference - so an agent working in one area loads a focused index instead of the whole site. llms.txt v2 defines what a subpath file means: it covers the pages under its path, and the most specific file applies. That also lets a site that controls only a path, such as a GitHub Pages project site, take part. Link each section file from the root index and verify both levels independently. Ora's `modular-llms-txt` check looks for this pattern by name: "Per-section llms.txt files (like /docs/llms.txt) so an agent working in one area gets a focused index instead of your whole site" ([ora.ai/api/checks](https://ora.ai/api/checks)).

Keep authoritative prices in sync across visible pages and a pricing.md representation when useful. See [Commercial and Entity Discovery](/docs/discovery/commercial-and-entity-discovery) for scope, provenance, and validation.
