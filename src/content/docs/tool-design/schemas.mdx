## Summary

Tool schemas define input parameters and output structure, enabling agents to reason reliably over results and avoiding hallucination. Three rules: (1) Flat structure (one or two levels is house advice, not an API limit; each level needs `additionalProperties: false` under OpenAI strict mode), (2) Every field must have description (.describe() in Zod, description in JSON Schema), (3) Enums over free text (constrain values where server enforces them). Input examples reduce errors. Declare output schemas so downstream tools get typed results. OpenAI strict mode requires every property in `required`, with optional fields made nullable rather than omitted; it supports nested `anyOf`, but not a root-level `anyOf` or unconstrained `any` branches.

- **Flat structures**: Max 1-2 levels deep
- **Descriptions**: Every field documented with examples
- **Enums**: Constrained values where possible
- **Input examples**: On parameters to guide agent
- **Output schema**: Declare return structure for downstream consumers
- **OpenAI strict mode**: every property stays in `required`; optional means nullable, not omitted

---

Tool schemas are the contract between the agent and the server. They define what parameters the agent can pass and what the server returns. Well-designed schemas reduce parameter errors and token cost, and give agents typed results to reason over.

## Input Schemas: Flat, Typed, Annotated

### The Three Rules

1. **Flat structure preferred.** Avoid deep nesting; one or two levels maximum. Deeply nested objects are harder for agents to reason about, and OpenAI strict mode requires `additionalProperties: false` and a full `required` list at every nested level, so each level of nesting adds another place to get that wrong.
2. **Every field must have a description.** Use `.describe()` in Zod or `description` in JSON Schema.
3. **Enums over free text.** Constrain values wherever the server enforces them.

### Zod Example

```typescript
import { z } from "zod";

const searchIssuesSchema = z
  .object({
    query: z
      .string()
      .describe(
        'Free text search. Examples: "status:Open", "assignee:alice@company.com", "label:bug"',
      ),

    assignee: z
      .string()
      .optional()
      .describe("Filter by assignee name or email. Omit to search all assignees."),

    status: z
      .enum(["Open", "In Progress", "Done", "Closed"])
      .optional()
      .describe("Issue workflow state. Omit to search all statuses."),

    priority: z
      .enum(["low", "medium", "high", "critical"])
      .optional()
      .describe("Severity: low=cosmetic, medium=feature, high=blocker, critical=outage"),

    limit: z
      .number()
      .int()
      .min(1)
      .max(100)
      .default(50)
      .describe("Max results to return. Default 50, capped at 100 for performance."),

    offset: z
      .number()
      .int()
      .min(0)
      .default(0)
      .describe(
        "Pagination offset. Use next_offset from the previous response to fetch the next page.",
      ),
  })
  .strict(); // Strict mode rejects unexpected fields
```

### JSON Schema Equivalent

```json
{
  "type": "object",
  "required": ["query"],
  "additionalProperties": false,
  "properties": {
    "query": {
      "type": "string",
      "description": "Free text search. Examples: \"status:Open\", \"assignee:alice@company.com\""
    },
    "status": {
      "type": "string",
      "enum": ["Open", "In Progress", "Done", "Closed"],
      "description": "Issue workflow state. Omit to search all statuses."
    },
    "limit": {
      "type": "integer",
      "minimum": 1,
      "maximum": 100,
      "default": 50,
      "description": "Max results to return. Default 50, capped at 100."
    }
  }
}
```

## Field-Level Best Practices

### UUID Fields

Use `.uuid()` to reject numeric IDs that look like strings:

```typescript
customer_id: z.string().uuid()
  .describe('The UUID of the customer. Get from `billing_list_customers` or `billing_get_customer`.'),
```

### Numeric Constraints

For monetary amounts and counts, use `.int()` to prevent `2.5 items`:

```typescript
amount_cents: z.number().int().positive().max(100_000_000)
  .describe('Invoice amount in cents (100 = $1.00). Max $1,000,000.'),

quantity: z.number().int().positive()
  .describe('Number of units. Must be at least 1.'),
```

### Dates and Times

Use regex constraints for format validation:

```typescript
due_date: z.string()
  .regex(/^\d{4}-\d{2}-\d{2}$/, 'Must be YYYY-MM-DD format')
  .describe('Payment due date in YYYY-MM-DD format (e.g., "2025-02-28"). Must be today or later.'),

start_time: z.string()
  .regex(/^\d{2}:\d{2}$/, 'Must be HH:MM format')
  .describe('Start time in 24-hour HH:MM format (e.g., "09:30").'),
```

### Enums for Constrained Values

Never accept free text when a fixed set is valid:

```typescript
// Bad:
status: z.string()
  .describe('Issue status'),

// Good:
status: z.enum(['open', 'in_progress', 'closed', 'archived'])
  .describe('Workflow state: open=new issue, in_progress=assigned, closed=resolved, archived=historical'),
```

### Optional Fields with Clear Defaults

Document what happens when optional fields are omitted:

```typescript
include_resolved: z.boolean().optional()
  .describe('Include closed/resolved items. Defaults to false (only show open issues).'),

sort_by: z.enum(['created', 'updated', 'priority']).optional()
  .describe('Sort order. Defaults to "updated" (most recently changed first).'),
```

### Arrays and Pagination

Cap arrays to prevent accidental giant payloads:

```typescript
labels: z.array(z.string()).max(10).optional()
  .describe('Filter by labels. Max 10 labels per search.'),

file_ids: z.array(z.string().uuid()).max(50).optional()
  .describe('File IDs to include. Max 50 files.'),
```

## Context Parameters vs Tool Parameters

An input schema should contain only the domain inputs the agent legitimately decides. Authentication tokens, session-derived user IDs, and internal system identifiers are context the execution layer injects at runtime - they must never appear as tool parameters. Asking the agent to supply them invites hallucinated or leaked credentials and couples the tool contract to implementation details.

```typescript
// Bad: agent is responsible for auth context it should never handle
{
  name: "create_document",
  schema: {
    properties: {
      auth_token: { type: "string" },      // Wrong: execution layer concern
      user_id: { type: "string" },         // Wrong: comes from session
      organization_id: { type: "string" }, // Wrong: comes from session
      title: { type: "string" },
      content: { type: "string" }
    }
  }
}

// Good: only domain inputs; auth/session context injected at runtime
{
  name: "create_document",
  schema: {
    properties: {
      title: { type: "string" },
      content: { type: "string" },
      folder_id: { type: "string", description: "Optional folder to place the document in" }
    },
    required: ["title"]
  }
}
```

Frameworks provide dedicated mechanisms for injecting this context outside the schema - LangChain's hidden `ToolRuntime` parameter (`runtime.context`), a separate runtime-context argument on the execute function (Mastra), or a closure over the request. Older injection patterns such as LangChain's `InjectedToolArg` are version-specific, so show how your host actually supplies the value. Keep the schema free of anything the session already knows.

## Output Schemas: Semantic Content

Declare an `outputSchema` when the tool's result will be consumed by other tools or stored in agent state. This enables downstream agents to receive typed structured data.

```typescript
const InvoiceOutputSchema = z.object({
  invoice_id: z.string().uuid().describe("Unique invoice identifier"),

  status: z.enum(["draft", "open", "paid", "void", "overdue"]).describe("Current invoice state"),

  amount_cents: z.number().int().positive().describe("Total invoice amount in cents"),

  currency: z.enum(["usd", "eur", "gbp"]).optional().describe("ISO 4217 currency code"),

  payment_url: z.string().url().optional().describe("Hosted payment page URL if invoice is open"),

  due_date: z
    .string()
    .regex(/^\d{4}-\d{2}-\d{2}$/)
    .optional()
    .describe("Payment due date in YYYY-MM-DD format"),
});

server.registerTool(
  "billing_create_invoice",
  {
    description: "Creates a new invoice and returns the invoice details...",
    inputSchema,
    outputSchema: InvoiceOutputSchema,
  },
  async (params) => {
    const invoice = await createInvoice(params);

    return {
      // Required when outputSchema is declared
      structuredContent: {
        invoice_id: invoice.id,
        status: invoice.status,
        amount_cents: invoice.amountCents,
        currency: invoice.currency,
        payment_url: invoice.hostedUrl ?? undefined,
        due_date: invoice.dueDate,
      },
      // Human-readable content for display
      content: [
        {
          type: "text",
          text: `Invoice ${invoice.id} created: $${(invoice.amountCents / 100).toFixed(2)} due ${invoice.dueDate}`,
        },
      ],
    };
  },
);
```

## Strict Mode for OpenAI Compatibility

When OpenAI strict mode is enabled, it requires `additionalProperties: false` at every object level and every property listed in `required` - including fields that are logically optional (see Nullable Parameters below). Strict mode is a setting, not a universal requirement: the API also supports non-strict function tools (`strict: false`), Chat Completions defaults to non-strict, and in Responses an omitted `strict` that can't be normalized to the strict subset falls back to non-strict calling. The OpenAI Agents SDK enables strict mode by default for schema-validated tools, so design for it when you target that SDK.

```typescript
// Zod
const schema = z.object({
  name: z.string(),
  email: z.string().email(),
}).strict();

// JSON Schema
{
  "type": "object",
  "additionalProperties": false,
  "required": ["name", "email"],
  "properties": {
    "name": { "type": "string" },
    "email": { "type": "string", "format": "email" }
  }
}
```

When a nested object exists, apply `additionalProperties: false` to it as well:

```typescript
const schema = z
  .object({
    customer: z
      .object({
        name: z.string(),
        email: z.string().email(),
      })
      .strict(), // Inner object must also be strict
    items: z.array(
      z
        .object({
          sku: z.string(),
          quantity: z.number().int(),
        })
        .strict(),
    ), // Each array element must be strict
  })
  .strict();
```

## Common Anti-Patterns

### Nullable Parameters

```typescript
// Bad: OpenAI strict mode has no concept of an omitted field; every
// property must be listed in `required`, so plain .optional() doesn't work
assignee: z.string().optional();

// Good: keep the field in `required`, make it nullable instead
assignee: z.string().nullable(); // emits { "type": ["string", "null"] }, stays in `required`
```

OpenAI strict mode requires every property to appear in the schema's `required` array - there's no way to mark a field as absent. To express "this field is optional," make it nullable (`"type": ["string", "null"]`) and have the caller pass `null` rather than omitting the key.

### Unions and Unconstrained Types

```typescript
// Bad: the unconstrained z.any() branch is rejected by OpenAI strict mode
result: z.union([
  z.object({ type: z.literal('success'), data: z.any() }),
  z.object({ type: z.literal('error'), message: z.string() })
])

// Good: constrained shapes, every field required, optional values nullable
result_type: z.enum(['success', 'error']),
result_data: z.object({ id: z.string(), summary: z.string() }).nullable(),
error_message: z.string().nullable(),
```

OpenAI strict mode supports nested `anyOf` (and internal `$ref` and recursive schemas) as long as every branch stays inside the supported subset; only a root-level `anyOf` is forbidden. Keeping to one or two levels of nesting is house advice for model reliability, not the API limit. The documented limits are 10 nesting levels and 5,000 object properties. Don't "fix" the pattern with `z.any().optional()`: that is incompatible with strict mode too, because unbounded `any` isn't a constrained schema and omitted optional properties conflict with the required-all rule.

### Free-Text Parameters That Accept Fixed Values

```typescript
// Bad
sort_order: z.string().describe("How to sort results"); // Vague; agent will guess

// Good
sort_order: z.enum(["ascending", "descending"]).describe("ascending=A-Z/0-9, descending=Z-A/9-0");
```

### Inconsistent ID Types

Use UUID everywhere or use explicit string + format constraints, never mix:

```typescript
// Bad
user_id: z.string().uuid(),
order_id: z.string(),  // Is this a UUID? a number?

// Good: all IDs are UUIDs
user_id: z.string().uuid(),
order_id: z.string().uuid(),
```

## Token Efficiency

Schemas are included in every tool-call request. Reduce schema size by:

- Using `.describe()` with short, punchy sentences (not paragraphs)
- Removing redundant descriptions that are obvious from the field name
- Deferring tool metadata until needed with provider-side tool search (`defer_loading` plus a tool search tool) or client-side `activeTools`
- Splitting a large tool with 30 parameters into two smaller tools

```typescript
// Bad: bloated description
due_date: z.string()
  .describe('The date that the customer is expected to pay the invoice. This should be set to a business day if possible, and you should avoid weekends and holidays. The format must be YYYY-MM-DD with a four-digit year, two-digit month, and two-digit day of the month.'),

// Good: concise but complete
due_date: z.string()
  .describe('Payment due date in YYYY-MM-DD format. Avoid weekends/holidays.'),
```

## Cross-Framework Compilation

Most current SDKs accept a Zod schema directly (the Vercel AI SDK's `inputSchema`, the OpenAI Agents SDK's `parameters`, MCP `registerTool`), so convert only when an API needs raw JSON Schema. Zod 4 has native conversion with `z.toJSONSchema()`:

```typescript
import { z } from "zod";

const schema = z
  .object({
    query: z.string(),
    limit: z.number().int().min(1).max(100).default(50),
  })
  .strict();

const jsonSchema = z.toJSONSchema(schema);
console.log(JSON.stringify(jsonSchema, null, 2));
```

The third-party `zod-to-json-schema` package is no longer actively maintained according to its maintainer, and version 3.25 supports Zod 4 only as a peer for schemas built from Zod 3 (`zod/v3`). Pin `zod/v3` for legacy code, or migrate to native conversion. Then validate the output against each target provider's subset (below); a valid JSON Schema isn't automatically an accepted tool schema.

## Provider Schema Limits

Checked against primary documentation on 2026-10-29. These are API limits, not recommendations to make tools that large.

- **OpenAI:** strict object schemas need `additionalProperties: false` at each object level and all properties required, with nullable values for logical optionals. Nested `anyOf` is allowed; a root `anyOf` is not. Limits: 5,000 properties, 10 nesting levels, 120,000 aggregate characters across names, enum and const strings, 1,000 enum values overall, and 15,000 characters for an individual enum with more than 250 values. See [supported schemas](https://developers.openai.com/api/docs/guides/structured-outputs#supported-schemas).
- **Anthropic:** strict tool use is GA, enabled per tool with `strict: true`, and uses its own JSON Schema subset. Unlike OpenAI, it supports optional properties. Combined strict-schema limits are 20 strict tools, 24 optional parameters and 16 union-typed parameters per request, with further grammar-complexity limits and a 180-second compilation timeout; non-strict tools don't count toward the 20-strict-tool ceiling. See [strict tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/strict-tool-use) and [schema complexity limits](https://platform.claude.com/docs/en/build-with-claude/structured-outputs#schema-complexity-limits).
- **Gemini:** function declarations use an OpenAPI-schema subset and very large or deep schemas can be rejected; the guide advises an active set of 10-20 tools. The API exposes mutually exclusive `parameters` (Schema object) and `parametersJsonSchema` (raw JSON Schema), so don't assume full JSON Schema support or copy OpenAI's strict-object rules. See [function calling](https://ai.google.dev/gemini-api/docs/function-calling).
- **AI SDK 7:** `inputSchema` accepts Zod or the SDK's `jsonSchema()` wrapper and validates generated input; provider `strict` remains provider-dependent. `ai@7.0.156` was current on 2026-10-28.
- **Mastra:** `createTool` has separate input and output schemas, takes the validated input as the first `execute` argument, and supports `requireApproval` and `mcp.annotations`. Core 1.80.0 was current on 2026-10-28.
- **LangChain:** runtime-context injection uses `ToolRuntime`; provider schema support depends on the model adapter, not on Pydantic alone.
