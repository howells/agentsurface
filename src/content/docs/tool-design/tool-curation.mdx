## Summary

Curate task-specific tool subsets from a centralized registry rather than loading everything at once. An API with 100 endpoints shouldn't show all 100 tools; expose a read-only set for auditors, a mutation set for admins, a focused set per workflow. This improves agent reasoning and reduces token cost. It is not an authorization boundary by itself: a tool hidden from a selection list can still be called if a client or deferred search surfaces it later, so recheck identity, permission and arguments at execution. Left unmanaged, a tool registry accumulates duplicate and overlapping tools - sprawl - that degrades selection accuracy the same way an oversized single request does.

- **Registry structure**: metadata (category, auth, rate limit), handler, schema
- **Subsets**: read-only, mutations, admin, dangerous (role-based)
- **Guidance, not a hard ceiling**: OpenAI calls "fewer than 20 functions available at the start of a turn" a soft suggestion; Anthropic's tool search tool notes selection accuracy degrades past 30-50 available tools
- **Dynamic selection**: keyword/BM25 filtering, embedding-based ranking, or Anthropic's server-side Tool Search Tool once a registry is large
- **Namespacing**: `billing__get_invoice` avoids name collisions across domains
- **Ownership**: every tool has an owner, a status (active/deprecated/experimental), and a removal path

---

An API might expose 100 endpoints. An agent should not see all 100 tools at once. Tool curation means curating a task-specific subset: read-only tools for auditors, mutation tools only for admins, a focused set for a specific workflow.

Agent frameworks route tool calls by matching the user's request against each tool's name and description, so every extra tool raises the chance of routing to the wrong one. There's no single hard ceiling across vendors: OpenAI describes "fewer than 20 functions available at the start of a turn" as a soft suggestion, and Anthropic notes that Claude's tool-selection accuracy degrades once a session exceeds roughly 30-50 available tools. Treat 20 as a review threshold regardless of provider - above it, curate a subset, namespace, or introduce dynamic selection rather than loading everything.

## Tool Registries

A tool registry is a centralized collection of all available tools with metadata. The agent system queries the registry to build task-specific subsets.

### Registry Structure

```typescript
// tools/registry.ts
import { z } from "zod";

interface ToolMetadata {
  name: string;
  description: string;
  schema: z.ZodSchema;
  handler: (params: any) => Promise<any>;
  category: "read" | "write" | "admin" | "dangerous";
  requiresAuth: boolean;
  rateLimit?: { requestsPerMinute: number };
  owner: string;
  status: "active" | "deprecated" | "experimental";
}

const toolRegistry: Record<string, ToolMetadata> = {
  search_issues: {
    name: "search_issues",
    description: "Search for issues by text, assignee, or status...",
    schema: searchIssuesSchema,
    handler: searchIssuesHandler,
    category: "read",
    requiresAuth: false,
    owner: "platform-team",
    status: "active",
  },
  delete_issue: {
    name: "delete_issue",
    description: "Permanently delete an issue (cannot be undone)...",
    schema: deleteIssueSchema,
    handler: deleteIssueHandler,
    category: "dangerous",
    requiresAuth: true,
    rateLimit: { requestsPerMinute: 1 },
    owner: "platform-team",
    status: "active",
  },
};

export const getAllTools = () => Object.values(toolRegistry);

export async function getToolsForUser(userId: string): Promise<ToolMetadata[]> {
  const user = await getUserPermissions(userId);
  return Object.values(toolRegistry).filter((tool) => {
    if (tool.status !== "active") return false;
    if (tool.requiresAuth && !user.authenticated) return false;
    if (tool.category === "admin" && !user.isAdmin) return false;
    if (tool.category === "dangerous" && !user.isDangerousActionsAllowed) return false;
    return true;
  });
}
```

This filter shapes what the model sees. Run the same permission check again when a tool executes, because a model, a client or a deferred search can still produce a call to a tool you filtered out of the list.

### Namespacing

Prefix tool names by domain to prevent collision and make ownership unambiguous - double underscore is the conventional separator:

```json
[
  {
    "name": "billing__get_invoice",
    "description": "Get invoice details from the billing system..."
  },
  {
    "name": "billing__create_invoice",
    "description": "Create a new invoice in the billing system..."
  },
  { "name": "docs__get_document", "description": "Get a document from the document store..." }
]
```

The namespace prefix makes the owning system clear even when the tool name itself is generic (`get_invoice` vs. `billing__get_invoice`).

## Role-Based Tool Kits

Different roles need different tools. Create curated kits per role, defined at a shared specification level rather than per agent instance:

```typescript
const toolKits = {
  auditor: {
    description: "Read-only access for compliance audits",
    tools: ["search_issues", "get_issue", "list_users", "get_user", "search_audit_logs"],
  },
  developer: {
    description: "Create and update issues, code review workflows",
    tools: [
      "search_issues",
      "create_issue",
      "update_issue",
      "search_pull_requests",
      "create_pull_request",
    ],
  },
  admin: {
    description: "Full access including dangerous operations",
    tools: [...Object.keys(toolRegistry)],
  },
};

export function getToolKitForRole(role: string): ToolMetadata[] {
  const kit = toolKits[role];
  if (!kit) throw new Error(`Unknown role: ${role}`);
  return kit.tools.map((name) => toolRegistry[name]).filter((t) => t !== undefined);
}
```

## Why Sprawl Happens

Left unmanaged, a tool registry grows monotonically: a new capability needs a tool, the existing set isn't checked for overlap, a slightly different variant gets added instead of extending the original, experimental tools are never removed, and deprecated endpoints stay registered because removing them feels risky. The result is a namespace with several tools that do roughly the same thing under different names - the agent may call the wrong one, call all of them, or fail to call any confidently.

## Dynamic Tool Selection

When a registry has more tools than a single session should see, don't load every definition upfront. Three approaches, in increasing order of setup cost:

### Keyword Filtering

The simplest approach for explicit categories - no embedding infrastructure required:

```typescript
function selectToolsByKeywords(userQuery: string, allTools: ToolMetadata[]): ToolMetadata[] {
  const keywords = userQuery.toLowerCase().split(/\s+/);
  return allTools.filter((tool) => {
    const toolText = `${tool.name} ${tool.description}`.toLowerCase();
    return keywords.some((kw) => toolText.includes(kw));
  });
}
```

### Active Tools (Vercel AI SDK)

```typescript
const result = await generateText({
  model,
  tools: allTools,
  activeTools: ["search_issues", "create_issue"], // Only these are loaded
  prompt: userMessage,
});
```

### Anthropic's Tool Search Tool

For Claude, the server-side tool search tool discovers and loads tool definitions on demand instead of front-loading everything. Mark tools you don't need up front with `defer_loading: true`, include a `tool_search_tool_bm25_20251119` (natural-language queries) or `tool_search_tool_regex_20251119` (Python-regex patterns) entry in `tools`, and Claude searches names, descriptions, and argument fields to discover and expand the tools it needs. A search returns up to five results by default, but the model can pass a `limit` from 1 to 10,000 and a request can contain up to 10,000 deferred tools, so five is a default result size, not a per-turn loading ceiling. BM25 queries are natural language up to 500 characters; regex patterns are capped at 200 characters. No beta header is required; it's a standard tool type. Deferred search composes with strict tool use, but the separate 20-strict-tool ceiling still applies. See [Anthropic's tool search tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool) for the request/response shape. OpenAI offers a comparable [tool search](https://developers.openai.com/api/docs/guides/tools-tool-search), so deferred loading isn't Anthropic-specific.

Two related Claude features cover different cases. Inline tool definitions (beta, 2026-09-22) let a mid-conversation system message add a tool with its full definition (`tool_addition` blocks under the `inline-tools-2026-09-15` beta header; MCP toolsets also need `mcp-client-2026-09-15`) without breaking the cached prefix; the tool search types above need neither header ([release notes](https://platform.claude.com/docs/en/release-notes/overview#september-22-2026)). Programmatic tool calling lets the model write code that calls a curated set of tools and keeps intermediate results out of its context; it needs a `code_execution_20260120` (or later) tool and `allowed_callers` on each tool the code may call ([guide](https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling)). To choose between them at runtime, read a model's capabilities from the Models API (2026-10-06): `capabilities.server_tools.code_execution` says the model accepts the server code-execution tool, and the separate top-level `capabilities.code_execution` says code can call the request's other tools ([release notes](https://platform.claude.com/docs/en/release-notes/overview#october-6-2026)).

### Embedding-Based Selection at Scale

Keyword and regex search match on literal text; embedding-based selection ranks tools by semantic similarity between the user's message and each tool's description, catching relevant tools even when the wording differs. This is the right choice when you're building the ranking yourself rather than delegating to a provider's server-side search:

1. Embed every tool description once at startup; cache the vectors (file or Redis) so restarts don't recompute them.
2. On each turn, compute cosine similarity between the user's message and the cached vectors; select the top ~12 candidates as a starting point, tuned against your tool set and evals.
3. Keep a small "always-active" set (web search, a `search_tools` meta-tool) that bypasses ranking, so the agent can always discover what the top-N selection missed.
4. Maintain a `relatedTools` map for write operations that depend on a read tool the embedding wouldn't surface on its own - e.g. `invoices_create` needs `customers_list` pre-loaded even though "create an invoice for $500" has no semantic overlap with "list customers." Keep this map to observed dependencies; don't add transitive ones speculatively.
5. Expose a `search_tools` meta-tool so the model can look outside the top-N selection when it needs a tool that didn't rank:

```typescript
server.registerTool(
  "search_tools",
  {
    description:
      "Search for a tool by name or capability. Use when you can't find the tool you need.",
    inputSchema: z.object({ query: z.string() }),
  },
  async (params) => {
    const results = await toolIndex.search(params.query, { maxResults: 5 });
    return { content: [{ type: "text", text: JSON.stringify(results) }] };
  },
);
```

Token savings are the main payoff, and they scale with how many definitions you stop sending: choosing 12 of 50 tools cuts the definition tokens by about three quarters if the tools are similar in size. That ratio is a hypothetical; measure a real registry with your tokenizer, including provider system overhead and cache state (see [Token Budget](/docs/tool-design/token-budget)). The tradeoffs are embedding latency (tens of milliseconds per request), a cold-start cost on the first request after a restart, and coverage - a tool outside the top-N is unreachable except through `search_tools`.

## Read-Only vs Mutating Kits

Distinguish safe (read) from risky (write) tools when assembling an agent's tool set:

```typescript
export const readOnlyKit = Object.values(toolRegistry).filter((t) => t.category === "read");
export const mutatingKit = Object.values(toolRegistry).filter((t) =>
  ["read", "write"].includes(t.category),
);
export const dangerousKit = Object.values(toolRegistry); // requires approval: see Human Approval

const auditAgent = agent({ tools: readOnlyKit, model: "claude-sonnet-5-5" });
const adminAgent = agent({
  tools: dangerousKit,
  model: "claude-opus-5-5",
  requireApproval: (toolName) => toolRegistry[toolName].category === "dangerous",
});
```

See [Human Approval](/docs/tool-design/human-approval) for the approval contract behind `requireApproval`.

## Tool Deprecation and Evolution

Tag tools with stability metadata and filter production/beta selections by it:

```typescript
export function selectToolsForProduction(allTools: ToolMetadata[]): ToolMetadata[] {
  return allTools.filter((t) => t.status === "active");
}
```

In descriptions, note deprecated tools and their replacement: `"DEPRECATED: Use \`search_issues\` instead. Removed 2026-12-01."` Never keep a deprecated tool registered out of fear of breakage - removal is safer than an agent discovering and calling a stale tool.

## Rate Limiting at the Registry Level

```typescript
async function executeToolWithRateLimit(toolName: string, params: any): Promise<any> {
  const tool = toolRegistry[toolName];
  if (!tool) throw new Error(`Unknown tool: ${toolName}`);
  if (tool.rateLimit) {
    const count = toolCallCounts.get(toolName) || 0;
    if (count >= tool.rateLimit.requestsPerMinute) {
      return {
        isError: true,
        content: [
          { type: "text", text: `Rate limit exceeded: ${tool.rateLimit.requestsPerMinute}/min.` },
        ],
      };
    }
    toolCallCounts.set(toolName, count + 1);
  }
  return await tool.handler(params);
}
```

## Sprawl Prevention Checklist

Before adding a new tool:

- [ ] Search the registry for an existing tool that covers this capability
- [ ] If a similar tool exists, is the new one genuinely different enough to warrant a separate entry?
- [ ] Does the new tool have an owner assigned?
- [ ] Is the tool name unique and does it follow the namespace convention?
- [ ] Will this tool be added to an approved role kit, or only used experimentally?
- [ ] Is the target agent's tool set already at or near the ~20-tool review threshold?

Review tool call metrics monthly - a tool with zero calls in 90 days is a removal candidate; a tool with a high error rate needs a description fix.
