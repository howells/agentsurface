## Summary

The examples below use recurring implementation patterns: toolset grouping, environment-driven configuration, structured error paths, lean responses, and startup-time tool selection. GitHub's large tool catalogue is managed via toolsets; Stripe limits tools by the permissions of a restricted API key; Vercel exposes deployment, project, and analytics tools. The code samples are simplified illustrations of these patterns, not the vendors' source.

- Toolset grouping: organize tools into named groups, enable via config
- Startup configuration: load toolsets/features at server start
- Environment-based: use env vars for API keys, endpoints, features
- Error recovery: structured errors guide agents toward retry or alternate paths
- Logging: write to stderr on stdio, OpenTelemetry on HTTP - the MCP logging facility is Deprecated in `2026-07-28`
- Each server keeps the tool list a given caller sees manageable by grouping tools or filtering them by permission

Production MCP servers from major platforms go beyond the spec in similar ways. The GitHub MCP server, Stripe's agent toolkit, and Vercel's MCP server each deal with tool explosion, auth flexibility, and deployment variety.

## GitHub MCP Server

The GitHub MCP server (`github/github-mcp-server`) is one of the most referenced open-source MCP implementations. It exposes GitHub operations - repositories, issues, pull requests, code search - to agents. Several of its design decisions are instructive.

### Toolset Grouping

GitHub's server exposes a large tool catalogue (see its README for the current list), which would be overwhelming without organization. It solves this through **toolset grouping**: tools are organized into named groups, and operators configure which groups are enabled:

```json
{
  "mcpServers": {
    "github": {
      "command": "github-mcp-server",
      "args": ["stdio"],
      "env": {
        "GITHUB_PERSONAL_ACCESS_TOKEN": "ghp_...",
        "GITHUB_TOOLSETS": "repos,issues,pull_requests"
      }
    }
  }
}
```

Tools in disabled toolsets are not registered - they do not appear in the `tools/list` response at all. Agents connected to a GitHub server configured for only `issues` and `pull_requests` see a manageable tool list focused on the work at hand, not the full catalogue. Code search lives under the `repos` toolset, and the server's default toolsets are `context`, `issues`, `pull_requests`, `repos`, and `users`.

The toolset configuration is read at startup, not per-request. Toolsets are an operator concern, not a user or agent concern:

```typescript
// Simplified version of GitHub's toolset pattern
const TOOLSETS: Record<string, RegisterFn[]> = {
  repos: [registerGetRepo, registerListRepos, registerCreateRepo, registerSearchCode],
  issues: [registerGetIssue, registerListIssues, registerCreateIssue, registerUpdateIssue],
  pull_requests: [registerGetPR, registerListPRs, registerCreatePR, registerMergePR],
};

const enabledToolsets = process.env.GITHUB_TOOLSETS?.split(",") ?? Object.keys(TOOLSETS);

for (const toolset of enabledToolsets) {
  const fns = TOOLSETS[toolset];
  if (!fns) throw new Error(`Unknown toolset: ${toolset}`);
  for (const fn of fns) fn(server, config);
}
```

### The --read-only Flag

GitHub's server accepts a `--read-only` flag that disables all tools that write, create, or delete:

```bash
github-mcp-server stdio --read-only
```

In read-only mode, only tools annotated with `readOnlyHint: true` are registered. This makes it safe to give an agent GitHub access in an automated pipeline without worrying about it opening issues or pushing code.

The implementation checks the flag during registration:

```typescript
export function registerCreateIssue(server: McpServer, config: Config): void {
  if (config.readOnly) return; // Skip registration entirely

  server.registerTool(
    "github_create_issue",
    {
      description: "Creates a new issue in a repository...",
      inputSchema: CreateIssueSchema,
      annotations: { readOnlyHint: false, destructiveHint: false },
    },
    async (params) => {
      /* ... */
    },
  );
}
```

### Environment-Driven Authentication

GitHub's server documents personal access token and OAuth setups. The snippet below is an illustrative application design, not GitHub's implementation, showing how one server binary can select an authentication strategy from the environment:

```typescript
function loadAuth(): Auth {
  if (process.env.GITHUB_PERSONAL_ACCESS_TOKEN) {
    return { type: "pat", token: process.env.GITHUB_PERSONAL_ACCESS_TOKEN };
  }

  if (process.env.GITHUB_APP_ID && process.env.GITHUB_APP_PRIVATE_KEY) {
    return {
      type: "app",
      appId: process.env.GITHUB_APP_ID,
      privateKey: process.env.GITHUB_APP_PRIVATE_KEY,
      installationId: process.env.GITHUB_APP_INSTALLATION_ID,
    };
  }

  if (process.env.GITHUB_OAUTH_TOKEN) {
    return { type: "oauth", token: process.env.GITHUB_OAUTH_TOKEN };
  }

  throw new Error(
    "No GitHub authentication configured. Set GITHUB_PERSONAL_ACCESS_TOKEN, " +
      "GITHUB_APP_ID + GITHUB_APP_PRIVATE_KEY, or GITHUB_OAUTH_TOKEN.",
  );
}
```

This pattern allows the same server binary to be deployed in different contexts without code changes. A developer uses a PAT; a CI pipeline uses a GitHub App; a user-facing product uses OAuth. For the credential options GitHub's server actually supports, use its README.

## Stripe MCP Server

Stripe's MCP server approach differs from GitHub's. Stripe offers three ways to use it:

1. **A hosted remote MCP server** at `https://mcp.stripe.com` - no deployment, with OAuth or agent API keys for authentication ([docs](https://docs.stripe.com/mcp))
2. **A local server package**, run with `npx -y @stripe/mcp --api-key=...`, where the tools available are controlled by the restricted API key you give it
3. **The `@stripe/agent-toolkit` npm package** - for embedding Stripe tools in your own agent

### Hosted Remote Server

```json
{
  "mcpServers": {
    "stripe": {
      "url": "https://mcp.stripe.com"
    }
  }
}
```

Stripe handles all deployment, scaling, versioning, and API compatibility. With OAuth, users authorize specific Stripe capabilities without sharing their API keys. This follows the authorization framework the MCP specification describes for HTTP servers.

### Agent Toolkit for Embedded Use

In the current toolkit, `StripeAgentToolkit` extends `McpServer`. It connects to Stripe's hosted MCP server as a client and proxies the tools your key is allowed to use, so you initialize it and then connect it to a transport rather than registering tools into another server:

```typescript
import { StripeAgentToolkit } from "@stripe/agent-toolkit/modelcontextprotocol";

const toolkit = new StripeAgentToolkit({
  secretKey: process.env.STRIPE_RESTRICTED_KEY!, // permissions come from the restricted key
  configuration: {}, // optional context (connected account, customer); check the package's Configuration type
});

await toolkit.initialize(); // connects to mcp.stripe.com and registers proxy tools
// toolkit is an McpServer: connect it to your transport as usual
```

Because the toolkit only proxies tools that the key's permissions allow, the restricted API key plays the same role as GitHub's toolset grouping: it limits which Stripe operations are exposed, preventing agents from reaching capabilities they should not have (refunds, subscription cancellations, account settings). Create the key with only the permissions the agent needs.

### Selective Tool Exposure

Limiting tools by permission is worth adopting in your own servers. Rather than exposing all tools to all users, scope tool availability to the requesting user's permissions. With the TypeScript SDK v2 `createMcpHandler`, the factory runs for each request and receives the verified `authInfo`, so it can register only the tools that caller may use:

```typescript
import { createMcpHandler, McpServer } from "@modelcontextprotocol/server";

function buildActionsConfig(scopes: string[]) {
  return {
    invoices: {
      create: scopes.includes("invoices:write"),
      read: scopes.includes("invoices:read"),
    },
    paymentIntents: {
      create: scopes.includes("payments:write"),
    },
  };
}

const handler = createMcpHandler((ctx) => {
  const server = new McpServer({ name: "billing-mcp", version: "1.0.0" });
  const actions = buildActionsConfig(ctx.authInfo?.scopes ?? []);

  // Only register tools the user is authorized to use
  if (actions.invoices.create) registerCreateInvoice(server, config);
  if (actions.invoices.read) registerListInvoices(server, config);
  if (actions.paymentIntents.create) registerCreatePaymentIntent(server, config);

  return server;
});
```

The handler does not verify tokens itself; verify the bearer token in front of it and pass the resulting `authInfo` to `handler.fetch`. Registration-time filtering is a convenience for the model, not the control: each tool must still check scopes when it runs.

## Vercel MCP Server

Vercel runs an official hosted MCP server at `https://mcp.vercel.com`, which uses OAuth and exposes deployment, project, and Web Analytics tools ([docs](https://vercel.com/docs/mcp/vercel-mcp)). Vercel's public documentation does not describe its internals, so the code below is an illustrative wrapper in the style of the `mcp-handler` package, not the production implementation.

```typescript
// Vercel's pattern: domain operations with auth-gated registration
export function registerDeploymentTools(
  server: McpServer,
  config: { token: string; teamId?: string },
): void {
  server.registerTool(
    "vercel_list_deployments",
    {
      description:
        "Lists recent deployments for a project. Returns deployment URLs, statuses, and git metadata.",
      inputSchema: z.object({
        project_id: z.string().describe("The Vercel project ID"),
        limit: z
          .number()
          .int()
          .min(1)
          .max(100)
          .optional()
          .default(20)
          .describe("Number of deployments to return (default 20, max 100)"),
      }),
      annotations: { readOnlyHint: true, openWorldHint: true },
    },
    async ({ project_id, limit }) => {
      const res = await fetch(
        `https://api.vercel.com/v6/deployments?projectId=${project_id}&limit=${limit}`,
        {
          headers: {
            Authorization: `Bearer ${config.token}`,
            ...(config.teamId ? { "x-vercel-team-id": config.teamId } : {}),
          },
        },
      );

      if (!res.ok) {
        return {
          isError: true,
          content: [{ type: "text", text: await res.text() }],
        };
      }

      const data = await res.json();
      return {
        content: [
          {
            type: "text",
            text: JSON.stringify(
              data.deployments.map((d: any) => ({
                id: d.uid,
                url: d.url,
                state: d.state,
                created_at: d.created,
                git_branch: d.meta?.githubCommitRef,
                git_message: d.meta?.githubCommitMessage,
              })),
            ),
          },
        ],
      };
    },
  );
}
```

The lean response pattern is clear here: rather than returning the full Vercel API response (which includes dozens of fields per deployment), only the fields an agent acts on are returned.

## Patterns They All Share

Reviewing GitHub, Stripe, and Vercel's approaches reveals five consistent patterns:

**1. Domain grouping.** Tools are organized by domain entity (repos, issues, deployments) rather than by operation type. This maps to how agents think - "I need to do something with invoices" routes to the invoices group.

**2. Auth kept out of tool code.** The hosted GitHub, Stripe, and Vercel servers document per-user OAuth (Stripe also offers agent API keys), while local setups pass tokens or restricted keys through the environment. Either way, no authentication method is hardcoded into the tool implementation.

**3. Selective tool exposure.** None of them expose their full API surface. GitHub has a `--read-only` flag and toolsets. Stripe limits tools by restricted-key permissions. The Vercel example above uses scope-gated registration. Agents get exactly the tools they need for the task at hand.

**4. Env-driven configuration.** Every behavioral variation - which tools to enable, which permissions to grant, which API endpoint to target - is controlled by environment variables. The server binary is environment-agnostic.

**5. Lean responses.** Tool responses return the minimum fields needed for the agent to proceed. Full API responses are never passed through directly.

These patterns address failures that show up as MCP deployments grow: tool sprawl, permission drift, environment-specific behavior, and oversized responses.
