## Summary

Two distinct Next.js-MCP patterns: next-devtools-mcp (dev environment tooling) and mcp-handler (production domain servers). The first exposes your dev environment to coding agents such as Claude Code through a project-root .mcp.json entry (other clients use their own config files). The second builds domain-specific MCP servers hosted inside a Next.js app. Both are useful but serve different purposes.

- next-devtools-mcp: local server, discovers the dev server's own `/_next/mcp` endpoint for errors, routes, and logs
- Setup: .mcp.json discovery in project root
- mcp-handler: production servers, domain-specific capabilities
- Use .mcp.json for local development; deploy domain servers separately
- Claude Code reads a project-root `.mcp.json`; Claude Desktop uses `claude_desktop_config.json` and Cursor uses `.cursor/mcp.json`, so add the same server entry to each client's own config

Next.js and MCP intersect in two completely different ways that are easy to conflate. The first is `next-devtools-mcp`, a tool that exposes your Next.js development environment to AI assistants. The second is building your own domain-specific MCP server hosted inside a Next.js application using `mcp-handler`. Both are useful, but they serve entirely different purposes.

The patterns below target Next.js 16 (App Router, Turbopack as the default bundler, Node 20+ floor) - the version this documentation site itself runs on.

## next-devtools-mcp: Dev Environment Tooling

`next-devtools-mcp` is a local MCP server that exposes your Next.js dev environment to Claude Code, Cursor, and other MCP-capable coding agents. It runs as a subprocess on your development machine alongside `next dev`. Agents connected to it can inspect errors, read routes, and query your Next.js application state without leaving the conversation.

**Setup:** Create a `.mcp.json` file in your project root:

```json
{
  "mcpServers": {
    "next-devtools": {
      "command": "npx",
      "args": ["-y", "next-devtools-mcp@latest"]
    }
  }
}
```

Next.js 16+ enables its own MCP endpoint by default at `http://localhost:3000/_next/mcp`. `next-devtools-mcp` scans common ports, discovers that endpoint on your running dev server, and connects automatically - no port flag or environment variable needed. Claude Code picks up a project-root `.mcp.json` when the project is opened. Other clients keep their MCP servers in their own config files (`claude_desktop_config.json` for Claude Desktop, `.cursor/mcp.json` for Cursor), so copy the same `next-devtools` entry there rather than assuming they read `.mcp.json`.

**Tools exposed by next-devtools-mcp:**

| Tool           | Description                                                                                                                                                             |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `nextjs_index` | Scans common ports for running Next.js 16+ dev servers and lists each one's runtime tools                                                                               |
| `nextjs_call`  | Invokes a runtime tool (`get_errors`, `get_logs`, `get_page_metadata`, `get_project_metadata`, `get_server_action_by_id`) on a discovered server, by port and tool name |
| `nextjs_docs`  | Points the agent at the version-matched docs bundled in `node_modules/next/dist/docs/`                                                                                  |
| `browser_eval` | Points the agent at the agent-browser CLI for browser automation                                                                                                        |

These tools are intentionally development-only. `next-devtools-mcp` does not run in production and does not expose any of your application's business logic or data.

## Building a Domain MCP Server with mcp-handler

If you want to expose your application's own capabilities through MCP - letting agents call your business logic, read your data, or trigger your workflows - you build a domain MCP server hosted inside your Next.js application.

Install the adapter. `mcp-handler` 2.x (2.3.0, 2026-10-07) needs `@modelcontextprotocol/server` ^2 and Zod 4; if you stay on the v1 SDK, pin `mcp-handler` 1.x and use its v1 options instead.

```bash
pnpm add mcp-handler @modelcontextprotocol/server zod
```

**Basic route handler** in `app/mcp/route.ts`:

```typescript
import { createMcpHandler } from "mcp-handler";
import { z } from "zod";

const handler = createMcpHandler((server) => {
  server.registerTool(
    "get_project_status",
    {
      description: "Returns the current status of a project by its slug.",
      inputSchema: z.object({
        project_slug: z.string().describe("The URL slug of the project to look up"),
      }),
    },
    async ({ project_slug }) => {
      const project = await db.projects.findBySlug(project_slug);

      if (!project) {
        return {
          isError: true,
          content: [{ type: "text", text: `Project '${project_slug}' not found.` }],
        };
      }

      return {
        content: [
          {
            type: "text",
            text: JSON.stringify({
              id: project.id,
              name: project.name,
              status: project.status,
              updated_at: project.updatedAt,
            }),
          },
        ],
      };
    },
  );
});

export const maxDuration = 60;

export { handler as GET, handler as POST };
```

`mcp-handler` returns a Web-standard handler that ignores the pathname, so it serves wherever you mount it (here `app/mcp/route.ts`, so `/mcp`). Version 2 removed `basePath` and the other route and transport options; there are no sessions, and GET and DELETE session requests return `405`. See [Transport Selection](./transports) for how the underlying route works.

**Connecting clients:** Point your MCP client at `https://your-app.vercel.app/mcp`.

## Organizing a Larger Domain Server

For servers with many tools, keep the route handler thin and move tool registration into a function - the same pattern described in [Server Architecture](./architecture). The registration callback runs once for the server, not per authenticated request, so tools read the caller's identity from the request context at call time:

```typescript
// lib/mcp/context.ts
import type { AuthInfo } from "@modelcontextprotocol/server";

export interface McpContext {
  userId: string;
  orgId: string;
  scopes: string[];
}

export function contextFromAuth(authInfo: AuthInfo | undefined): McpContext {
  if (!authInfo) throw new Error("Unauthenticated request");
  const { userId, orgId } = authInfo.extra as { userId: string; orgId: string };
  return { userId, orgId, scopes: authInfo.scopes };
}
```

```typescript
// lib/mcp/server.ts
import type { McpServer } from "@modelcontextprotocol/server";
import { registerProjectTools } from "./tools/projects.js";
import { registerDeploymentTools } from "./tools/deployments.js";
import { registerTeamTools } from "./tools/teams.js";

export function registerTools(server: McpServer): void {
  registerProjectTools(server);
  registerDeploymentTools(server);
  registerTeamTools(server);
}

// In a tool file, handlers take the request context as their second argument:
//   async ({ project_slug }, ctx) => {
//     const { orgId } = contextFromAuth(ctx.http?.authInfo);
//     ...
//   }
```

```typescript
// app/mcp/route.ts
import { createMcpHandler, withMcpAuth } from "mcp-handler";
import type { AuthInfo } from "@modelcontextprotocol/server";
import { registerTools } from "@/lib/mcp/server";
import { validateToken } from "@/lib/auth/validate-token";

const mcpHandler = createMcpHandler((server) => registerTools(server), {
  serverInfo: { name: "my-app", version: "1.0.0" },
});

// Receives the request and the bearer token (undefined when none was sent)
async function authenticate(req: Request, bearerToken?: string): Promise<AuthInfo | undefined> {
  if (!bearerToken) return undefined;
  const { userId, orgId, scopes } = await validateToken(bearerToken);
  return { token: bearerToken, clientId: userId, scopes, extra: { userId, orgId } };
}

const handler = withMcpAuth(mcpHandler, authenticate, { required: true });

export const maxDuration = 60;

export { handler as GET, handler as POST };
```

The `withMcpAuth` wrapper returns one handler function, which you export under the method names you serve. It calls `authenticate` on every request; with `required: true` (the default is `false`) it rejects requests without valid authentication with a `401` and an RFC 9728 `WWW-Authenticate` challenge before the handler runs. Tool handlers read the verified `AuthInfo` from `ctx.http?.authInfo`.

## Stateless Mode Is Now Protocol-Level

Next.js on Vercel runs as serverless functions. Fluid Compute can reuse an instance and serve concurrent invocations from it, but you cannot count on any particular request landing on the same instance, so in-memory state is not a safe place for anything you need to keep - and the `mcp-handler` package serves requests statelessly. Under the current `2026-07-28` MCP specification, every MCP deployment target is stateless by protocol: the protocol removes the `initialize` handshake and protocol-level sessions outright (SEP-2567, SEP-2575). A long-running container behind Streamable HTTP is in exactly the same position as a Vercel function - there is no session for either one to hold.

The pattern below - an identifier passed as an ordinary tool argument, with state kept in an external store - is what the spec's own "Stateful Tools" guidance describes as the correct way to carry state across calls now that MCP has no protocol-level session. Build it this way regardless of where the server runs.

For tools that require session state across calls, store state externally:

```typescript
import { createMcpHandler } from "mcp-handler";
import { z } from "zod";
import { kv } from "@vercel/kv";

const handler = createMcpHandler((server) => {
  server.registerTool(
    "continue_analysis",
    {
      description:
        "Continues a multi-step analysis started with start_analysis. " +
        "Requires the session_id returned by start_analysis.",
      inputSchema: z.object({
        session_id: z.string().describe("Session ID from start_analysis"),
        next_step: z.enum(["summarize", "compare", "export"]),
      }),
    },
    async ({ session_id, next_step }) => {
      const state = await kv.get<AnalysisState>(`analysis:${session_id}`);

      if (!state) {
        return {
          isError: true,
          content: [
            {
              type: "text",
              text: `Session ${session_id} not found or expired. Call start_analysis to begin a new analysis.`,
            },
          ],
        };
      }

      // Process next step using stored state
      const result = await processStep(state, next_step);

      // Update stored state
      await kv.set(`analysis:${session_id}`, result.newState, { ex: 3600 });

      return {
        content: [{ type: "text", text: JSON.stringify(result.output) }],
      };
    },
  );
});
```

## maxDuration and Fluid Compute

Long-running tools - those that process files, call slow external APIs, or run batch operations - need a `maxDuration` large enough for the operation to complete. Vercel Functions run on Fluid Compute by default, which gives the Hobby plan a 300-second (5-minute) default and maximum.

```typescript
// Route-level configuration
export const maxDuration = 300; // Hobby default and maximum under Fluid Compute
```

Pro and Enterprise default to 300 seconds too, but can raise `maxDuration` up to 800 seconds, or to 1800 seconds (30 minutes) through the extended-duration beta:

```json
{
  "functions": {
    "app/mcp/route.ts": {
      "maxDuration": 800
    }
  }
}
```

Fluid Compute keeps the function instance alive between requests and allows concurrent execution. This lets one instance serve concurrent requests and keep a streaming response open while work proceeds, within the maximum duration.

<Callout type="info">
  Durations above 800 seconds need the extended-duration beta and Pro or Enterprise. Streaming
  heartbeats keep idle intermediaries from closing the connection, but they do not extend the
  function's maximum duration. For work that can outlast the limit, hand it to durable or background
  execution and report progress through the Tasks extension or polling.
</Callout>

## Environment Variables for MCP in Next.js

MCP route handlers run as server-side code and have access to all server-side environment variables. Do not prefix MCP-related secrets with `NEXT_PUBLIC_` - that exposes them to the browser bundle.

```bash
# .env.local (development)
MCP_AUTH_SECRET=your-bearer-token
DATABASE_URL=postgres://...
STRIPE_API_KEY=sk_test_...

# Never:
NEXT_PUBLIC_MCP_AUTH_SECRET=... # ← This goes into the browser bundle
```

Access them in your route handler via `process.env.VARIABLE_NAME` - they are available without any additional configuration in Next.js server components and route handlers.
