## Summary

The transport layer affects latency, deployment, scalability, and state management. Stdio is simplest (subprocess, no network), best for local development. Streamable HTTP enables distributed deployment and horizontal scaling; the older standalone HTTP+SSE transport has been deprecated since the `2025-03-26` revision. Write logs to stderr only; stdout is reserved for MCP JSON-RPC frames. Choose transport early - rearchitecting for a different one is painful.

- Stdio: simplest, no network, logs to stderr
- HTTP (Streamable HTTP): bidirectional, most scalable, the default remote transport
- Standalone HTTP+SSE: deprecated since the `2025-03-26` revision - migration path only
- Select early in design - transport affects lifecycle and state management
- Always write logs to stderr, never stdout
- Prefer stateless mode: `2026-07-28` removes sessions and the `Mcp-Session-Id` header entirely

The transport layer determines how messages flow between the MCP client and your server. The choice affects latency, deployment model, horizontal scalability, and how you handle authentication. Getting it wrong early is painful to unwind - a server designed for stdio cannot be trivially converted to HTTP without rethinking connection lifecycle and state management.

## Stdio Transport

Stdio is the simplest transport. The client launches your server as a subprocess and communicates over the process's stdin and stdout. There is no network involved.

```typescript
// cli.ts
import { StdioServerTransport } from "@modelcontextprotocol/server/stdio";
import { createServer } from "./server.js";

const server = createServer({
  stripeApiKey: process.env.STRIPE_API_KEY!,
  databaseUrl: process.env.DATABASE_URL!,
});

const transport = new StdioServerTransport();
await server.connect(transport);
// Process stays alive, reading from stdin
```

**Write logs to stderr, never stdout.** The MCP protocol uses stdout exclusively for message exchange. Any writes to stdout that are not valid MCP JSON-RPC frames will corrupt the transport.

```typescript
// WRONG: corrupts the stdio transport
console.log("Server started");

// CORRECT: stderr is safe for diagnostic output
console.error("Server started");

// ALTERNATIVE (2025-11-25): the MCP logging facility
await server.sendLoggingMessage({
  level: "info",
  logger: "billing-mcp",
  data: "Server started",
});
```

<Callout type="warn">
  Current `2026-07-28` behavior: the Logging feature is Deprecated (SEP-2577) and `logging/setLevel`
  is removed, with log level moving to a per-request `io.modelcontextprotocol/logLevel` value in
  `_meta`. The MCP logging facility keeps working through the 12-month deprecation window, but new
  servers should write diagnostics to stderr on stdio and emit OpenTelemetry spans on HTTP instead.
  The stderr rule above is unaffected and remains the safest default on either revision.
</Callout>

**Client configuration for stdio (Claude Desktop example):**

```json
{
  "mcpServers": {
    "billing": {
      "command": "node",
      "args": ["/path/to/billing-mcp/dist/cli.js"],
      "env": {
        "STRIPE_API_KEY": "sk_live_...",
        "DATABASE_URL": "postgres://..."
      }
    }
  }
}
```

**When to use stdio:**

- Local development tools running on a developer's machine
- CLI-invoked servers where every invocation is a fresh session
- Tools that need to access local filesystem or system resources
- Situations where zero network overhead matters
- Servers that should not be exposed to network traffic

## Streamable HTTP Transport

Streamable HTTP is the correct transport for servers deployed as cloud services. It exposes a single HTTP endpoint (conventionally `/mcp`) that accepts POST requests. Responses can be single JSON objects or SSE streams, depending on whether the operation requires streaming.

The example below is the sessionful `2025-11-25` pattern on the v1 SDK (`@modelcontextprotocol/sdk` 1.x, kept maintained for compatibility). Use it only for clients that still need it; for new servers use the stateless handler in the next section.

```typescript
// src/http-server.ts (SDK v1, 2025-11-25 sessionful compatibility)
import express from "express";
import { StreamableHTTPServerTransport } from "@modelcontextprotocol/sdk/server/streamableHttp.js";
import { createServer } from "./server.js";

const app = express();
app.use(express.json());

const transports = new Map<string, StreamableHTTPServerTransport>();

app.post("/mcp", async (req, res) => {
  const sessionId = req.headers["mcp-session-id"] as string | undefined;

  let transport: StreamableHTTPServerTransport;

  if (sessionId && transports.has(sessionId)) {
    transport = transports.get(sessionId)!;
  } else {
    // New session - create a fresh transport and server pair
    transport = new StreamableHTTPServerTransport({
      sessionIdGenerator: () => crypto.randomUUID(),
      onsessioninitialized: (id) => {
        transports.set(id, transport);
      },
    });

    transport.onclose = () => {
      if (transport.sessionId) {
        transports.delete(transport.sessionId);
      }
    };

    const server = createServer(loadConfig());
    await server.connect(transport);
  }

  await transport.handleRequest(req, res, req.body);
});

// Handle GET for SSE streaming and DELETE for session termination
app.get("/mcp", async (req, res) => {
  const sessionId = req.headers["mcp-session-id"] as string | undefined;
  if (!sessionId || !transports.has(sessionId)) {
    res.status(404).json({ error: "Session not found" });
    return;
  }
  await transports.get(sessionId)!.handleRequest(req, res);
});

app.delete("/mcp", async (req, res) => {
  const sessionId = req.headers["mcp-session-id"] as string | undefined;
  if (sessionId && transports.has(sessionId)) {
    transports.get(sessionId)!.close();
    transports.delete(sessionId);
  }
  res.status(204).send();
});

app.listen(3000);
```

<Callout type="warn">
  Current `2026-07-28` behavior: sessions are removed from the protocol (SEP-2567). The
  `Mcp-Session-Id` header disappears, the GET endpoint that carried the server-to-client stream is
  replaced by a `subscriptions/listen` request, and the DELETE endpoint that terminated a session
  has nothing left to terminate. Cross-call state moves to explicit server-minted handles that the
  client passes back as ordinary tool arguments. POSTs also gain two required headers, `Mcp-Method`
  and `Mcp-Name` (SEP-2243), with custom headers namespaced under `x-mcp-header`. The code above is
  the correct shape for `2025-11-25` and the v1 SDK; the stateless pattern in the next section is
  the one that matches the current revision, so prefer it for new servers.
</Callout>

## Stateless Mode for Horizontal Scaling

The stateful session map above does not scale horizontally - sessions created on one instance are not visible to another. `2026-07-28` removes sessions from the protocol, so the current TypeScript SDK (v2, `@modelcontextprotocol/server`) serves each request independently with `createMcpHandler`. It takes a factory that builds a server for each request, answers 2026-07-28 traffic on the modern path, and by default serves 2025-era clients through a stateless legacy fallback. Setting `sessionIdGenerator: undefined` on a v1 transport only disables session tracking in v1 code; it does not make that code speak the 2026 protocol.

```typescript
// src/http-handler.ts
import { createMcpHandler } from "@modelcontextprotocol/server";
import { createServer } from "./server.js";

const handler = createMcpHandler(() => createServer(loadConfig()));

// Any Web-standard host: Request in, Response out.
export default {
  fetch: (request: Request) => handler.fetch(request),
};
```

The handler does no Origin or Host validation and no token verification. Mount the SDK's host and origin validation middleware, and your bearer-token check, in front of it (see [MCP Authentication](./authentication)). To keep serving legacy sessionful clients from an existing deployment, route them in your own code with `isLegacyRequest` in front of a `legacy: "reject"` handler.

In a stateless server every request is independent, which maps cleanly to serverless functions - and it is the model `2026-07-28` requires. For operations that need state across calls - maintaining context between tool invocations in a multi-turn conversation - store state in Redis or another shared store and key it on a server-minted handle that the client passes back as an ordinary tool argument. That works on both revisions and does not depend on transport-level session tracking. There is no `setSessionState` on `McpServer`; keep application state in your own code behind explicit tools:

```typescript
server.registerTool(
  "workspace_open",
  { description: "Opens a workspace and returns its workspace_id.", inputSchema: z.object({}) },
  async () => {
    const workspaceId = crypto.randomUUID();
    await redis.set(`mcp:workspace:${workspaceId}`, JSON.stringify({ items: [] }), "EX", 3600);
    return { content: [{ type: "text", text: JSON.stringify({ workspace_id: workspaceId }) }] };
  },
);

server.registerTool(
  "workspace_add_item",
  {
    description: "Adds an item to a workspace opened with workspace_open.",
    inputSchema: z.object({ workspace_id: z.string().uuid(), item: z.string().max(200) }),
  },
  async ({ workspace_id, item }) => {
    const raw = await redis.get(`mcp:workspace:${workspace_id}`);
    if (!raw) {
      return {
        isError: true,
        content: [
          {
            type: "text",
            text: `Workspace ${workspace_id} not found or expired. Call workspace_open to start a new one.`,
          },
        ],
      };
    }
    const state = JSON.parse(raw) as { items: string[] };
    state.items.push(item);
    await redis.set(`mcp:workspace:${workspace_id}`, JSON.stringify(state), "EX", 3600);
    return {
      content: [{ type: "text", text: `Workspace now holds ${state.items.length} items.` }],
    };
  },
);
```

## SSE as a Standalone Transport

The older HTTP+SSE transport (`/sse` for the stream, `/message` for posting) has been deprecated since the `2025-03-26` MCP specification revision, and is formally Deprecated under the feature lifecycle policy introduced in `2026-07-28`. Do not build new servers against it. Streamable HTTP supersedes it and supports SSE as an optional response mode when the server needs to stream a long-running tool result.

## Transport Decision Guide

```
Deployment context                     Transport
────────────────────────────────────── ─────────────────
Developer's local machine              Stdio
CI/CD runner, scripted automation      Stdio
Serverless function (Vercel, Lambda)   Streamable HTTP (stateless)
Long-running container (single)        Streamable HTTP (stateless; state in your own store)
Horizontally scaled service            Streamable HTTP (stateless + Redis)
Legacy 2025-11-25 clients only          Streamable HTTP (stateful, SDK v1)
Embedded in CLI tool                   Stdio
Shared public service (multiple users) Streamable HTTP + OAuth
```

## Production Deployment on Vercel

Vercel's serverless platform requires specific configuration for MCP servers due to request duration limits and streaming behavior.

**Route handler for Next.js App Router** (`mcp-handler` 2.x, which requires `@modelcontextprotocol/server` ^2 and Zod 4):

```typescript
// app/mcp/route.ts
import { createMcpHandler } from "mcp-handler";
import { registerCreateInvoice } from "@/lib/billing-mcp/tools/create-invoice";

const config = {
  stripeApiKey: process.env.STRIPE_API_KEY!,
  databaseUrl: process.env.DATABASE_URL!,
};

// The first argument receives the MCP server to register tools on; the second is one options object.
const handler = createMcpHandler(
  (server) => {
    registerCreateInvoice(server, config);
    // ...register the remaining tools, resources, and prompts
  },
  { serverInfo: { name: "billing-mcp", version: "1.0.0" } },
);

export const maxDuration = 300; // seconds - the Hobby default and maximum under Fluid Compute

export { handler as GET, handler as POST };
```

Vercel Functions run on Fluid Compute by default, which lets one function instance serve concurrent requests instead of blocking on a single SSE stream. You do not need to opt in.

<Callout type="info">
  Duration defaults and maximums under Fluid Compute: Hobby gets 300 seconds (5 minutes), both
  default and maximum. Pro and Enterprise default to 300 seconds with an 800-second maximum, and can
  request up to 1800 seconds (30 minutes) through the extended-duration beta. For tools with
  long-running operations (file processing, external API calls), set `maxDuration` explicitly or use
  a streaming response to heartbeat the connection while work proceeds.
</Callout>

**The `mcp-handler` package** (2.3.0, 2026-10-07) serves the sessionless `2026-07-28` revision with a legacy stateless fallback, and returns a Web-standard handler that ignores the pathname, so you mount it at whatever route you want. Version 2 removed `basePath`, the SSE and streamable-endpoint options, `redisUrl`, `maxDuration`, and `sessionIdGenerator`, and GET/DELETE session requests now return `405`. If you stay on SDK v1, pin `mcp-handler` 1.x and its v1 options deliberately instead of installing the latest.

## Using mcp-handler with Dynamic Transport Selection

For servers that need to support both stdio (local) and HTTP (deployed), expose the transport as a runtime decision based on how the process was invoked:

```typescript
// src/main.ts
import { createServer } from "./server.js";

// If invoked via node cli.js, use stdio
// If invoked via HTTP (detected by PORT env var), use HTTP
if (process.env.PORT) {
  const { startHttpServer } = await import("./http-server.js");
  // The HTTP path takes a factory so each request gets its own server
  await startHttpServer(() => createServer(loadConfig()), Number(process.env.PORT));
} else {
  const { StdioServerTransport } = await import("@modelcontextprotocol/server/stdio");
  const server = createServer(loadConfig());
  const transport = new StdioServerTransport();
  await server.connect(transport);
}
```

This pattern avoids bundling HTTP server dependencies into the stdio binary and vice versa - each transport path imports its dependencies lazily.

<Callout type="warn">
  On the v1 SDK's sessionful Streamable HTTP transport, never use the same `McpServer` instance
  across multiple transport connections; create a new server instance per connection. With the
  current per-request handlers (`createMcpHandler` in SDK v2, `mcp-handler` 2.x), the factory or
  registration callback you pass is what builds the server for each request, so follow that adapter
  rather than deriving instance lifetime from the removed session model.
</Callout>
