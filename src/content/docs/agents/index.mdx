## Summary

Part 1 of this guide makes an existing product usable by agents: discovery, APIs, tools, CLIs, MCP servers, authentication, error handling, and retrieval. This part is different. It is a condensed, current-practice reference for teams **building** agents of their own - choosing a runtime, wiring memory, running multi-agent systems, and giving agents browser or sandbox access.

Each page states what good practice is right now and points at the tools and platforms that implement it, in [the tooling catalog](/docs/tooling-catalog). Framework ecosystem lists (Mastra's integrations, for example) are used as sources without being treated as the authority.

## Design Defaults

A handful of defaults apply regardless of which framework or platform a team picks. They come up on nearly every page below, so they are stated once here.

- **Tools over knowledge.** Business state, retrieval, and side effects belong in tools, not in the prompt. If a value could change tomorrow, it should not live only in the system prompt - see [Tool Design](/docs/tool-design).
- **Narrow ownership.** An agent should own one decision boundary, not a department. A "billing dispute triage agent" is easier to evaluate and less likely to hallucinate tool usage than a "customer operations agent."
- **Workflow before agent.** If the sequence is predictable, scaffold a deterministic workflow and drop an agent in only at the steps that need judgment: classifying intent, synthesizing tradeoffs, choosing among candidates.
- **Bounded loops only.** Every production agent needs an explicit step budget, a stop condition, and a failure path for when the budget runs out. A loop that needs more than 10 steps is usually a sign the boundary is wrong, not that the budget should grow.
- **Prompt as configuration.** See [Prompts and Configuration](/docs/agents/prompts-and-configuration) for the pattern; keep tenant selection, branching business logic, and access decisions out of prompt text entirely.
- **Memory is earned.** Start with none. Add message history, then working memory, then semantic recall only when the product need is concrete - see [Memory](/docs/agents/memory).
- **Eval-first.** A scaffold that creates an agent without a success case, a wrong-tool case, and a malformed-arguments case is incomplete. See [Evaluation Framework](/docs/testing/evaluation-framework) in Part 1.
