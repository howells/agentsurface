## Summary

DPoP binds an access token to a client's public key. On every request, the client signs a proof JWT with the request method, URI, and a unique jti (nonce). If the token is stolen without the private key, an attacker cannot create a valid proof, making the token useless.

```
Client: (with private key)        Server: (verifies)
  Generate keypair               Extract public key from DPoP
  Sign DPoP proof                Verify signature
  Send token + DPoP              Check htm, htu, ath, jti
```

- Each request includes a DPoP proof: unique jti, htm (method), htu (URI), iat (timestamp), and ath (access-token hash)
- Server validates signature, claim values, ath, and jti uniqueness (prevents replay)
- Token includes a `cnf.jkt` claim: thumbprint of the DPoP proof's JWK
- Required for financial operations, user data access, administrative actions
- Use ES256 or Ed25519 for DPoP proof signing

When an access token is stolen - via a log, a memory dump, a man-in-the-middle attack - the attacker can replay it against the resource server until it expires. Demonstrating Proof-of-Possession (DPoP, RFC 9449) solves this by binding the token to the client's public key. If the token is stolen, it cannot be replayed because the attacker lacks the private key.

Use DPoP for high-value operations and agent-to-agent communication where token compromise is a real risk.

## How DPoP Works

The client generates an Ed25519 or ES256 keypair. On every request, the client creates a `DPoP` proof JWT that includes:

- `htm` (HTTP Method): the request method (GET, POST, etc.)
- `htu` (HTTP URI): the request URI without its query or fragment
- `iat` (Issued At): Unix timestamp
- `jti` (JWT ID): unique nonce, prevents replay of the same proof
- `ath` (Access Token Hash): base64url SHA-256 of the access token, required when calling a protected resource
- `nonce`: only when the server has issued one in a `DPoP-Nonce` header

The client sends the token with the `DPoP` authorization scheme (`Authorization: DPoP <token>`, not `Bearer`) plus the `DPoP` proof header. The server validates:

1. The proof has `typ: dpop+jwt`, an allowed asymmetric `alg`, and a valid signature from the public JWK embedded in its own header (no prior key registration is needed)
2. The `htm` and `htu` match the current request, comparing `htu` without query or fragment
3. The `ath` matches the hash of the presented access token
4. The `jti` has not been seen within the acceptance window (prevents reuse)
5. The `iat` is recent (prevents old proofs from being replayed), and `nonce` matches if the server requires one
6. The JWK thumbprint matches the token's `cnf.jkt` binding

If the token is stolen without the private key, an attacker cannot create a valid DPoP proof for a different URI, so the stolen token is useless.

## Client-Side: Generating DPoP Proofs

```typescript
import { SignJWT, exportJWK, generateKeyPair } from "jose";
import { createHash, randomUUID } from "node:crypto";

// Generate keypair once and store securely
const { publicKey, privateKey } = await generateKeyPair("ES256");
const { kty, crv, x, y } = await exportJWK(publicKey); // public members only

async function generateDPopProof(
  method: string,
  uri: string,
  accessToken: string,
  nonce?: string,
): Promise<string> {
  const url = new URL(uri);
  const htu = `${url.origin}${url.pathname}`; // no query or fragment

  return new SignJWT({
    jti: randomUUID(), // Unique per request
    htm: method, // GET, POST, etc.
    htu,
    iat: Math.floor(Date.now() / 1000),
    ath: createHash("sha256").update(accessToken).digest("base64url"),
    ...(nonce ? { nonce } : {}), // from a DPoP-Nonce response header
  })
    .setProtectedHeader({ alg: "ES256", typ: "dpop+jwt", jwk: { kty, crv, x, y } })
    .sign(privateKey);
}

// On every request
const method = "GET";
const uri = "https://api.example.com/invoices?status=open";
const dpopProof = await generateDPopProof(method, uri, accessToken);

const res = await fetch(uri, {
  method,
  headers: {
    Authorization: `DPoP ${accessToken}`,
    DPoP: dpopProof,
  },
});
```

The `jti` must be unique per request to prevent replay. Use a UUID. If the server answers `401` with a `DPoP-Nonce` header, retry once with that value in the `nonce` claim.

## Server-Side: Validating DPoP Proofs

```typescript
import { calculateJwkThumbprint, decodeProtectedHeader, importJWK, jwtVerify } from "jose";
import { createHash } from "node:crypto";

// Store of seen JTIs to prevent replay. Keep each entry for the whole
// acceptance window below (iat skew plus max age); use Redis in production.
const seenJtis = new Set<string>();

async function validateDPopProof(
  dpopHeader: string,
  method: string,
  uri: string,
  accessToken: string,
): Promise<{ thumbprint: string }> {
  // Read the header first, without verifying: the proof's own public key
  // is embedded in it, so there is nothing to verify against yet.
  const protectedHeader = decodeProtectedHeader(dpopHeader);

  if (protectedHeader.typ !== "dpop+jwt" || !protectedHeader.jwk) {
    throw new Error("Not a DPoP proof, or missing public key in header");
  }

  const publicKey = await importJWK(protectedHeader.jwk, protectedHeader.alg);

  // Now verify the signature, allowing only asymmetric algorithms
  const { payload } = await jwtVerify(dpopHeader, publicKey, {
    algorithms: ["ES256", "EdDSA"],
    typ: "dpop+jwt",
  });

  // Verify claims
  const now = Math.floor(Date.now() / 1000);
  if ((payload.iat as number) > now + 60) {
    throw new Error("DPoP proof issued in the future");
  }
  if ((payload.iat as number) < now - 300) {
    throw new Error("DPoP proof is stale");
  }

  if (payload.htm !== method) {
    throw new Error(`DPoP htm does not match request method: ${payload.htm} vs ${method}`);
  }

  // htu excludes query and fragment on both sides
  const target = new URL(uri);
  const proofTarget = new URL(payload.htu as string);
  if (`${proofTarget.origin}${proofTarget.pathname}` !== `${target.origin}${target.pathname}`) {
    throw new Error(`DPoP htu does not match request URI: ${payload.htu} vs ${uri}`);
  }

  // ath binds the proof to this access token
  const ath = createHash("sha256").update(accessToken).digest("base64url");
  if (payload.ath !== ath) {
    throw new Error("DPoP ath does not match the presented access token");
  }

  // Check JTI for replay
  const jti = payload.jti as string;
  if (seenJtis.has(jti)) {
    throw new Error("DPoP JTI has been replayed");
  }
  seenJtis.add(jti);

  // Return the thumbprint for comparison with the token's cnf.jkt
  const thumbprint = await calculateJwkThumbprint(protectedHeader.jwk);
  return { thumbprint };
}
```

## Binding DPoP to Access Tokens

When issuing an access token, the authorization server includes the DPoP proof's JWK thumbprint in the token's `cnf.jkt` claim (RFC 9449 §6.1; `dpop_jkt` is the parameter the client sends in the authorization request, not a token claim):

```json
{
  "sub": "client_01HV3K8MNP",
  "aud": "https://api.example.com/",
  "scope": "invoices:read",
  "cnf": {
    "jkt": "fUHyO2r...rg"
  },
  "iat": 1700000000,
  "exp": 1700003600
}
```

On every request, the server verifies:

1. The DPoP proof is valid (signature, `typ`, `htm`, `htu`, `iat`, `ath`, `jti`, and `nonce` if required)
2. The DPoP proof's JWK thumbprint matches the token's `cnf.jkt` claim

If an attacker steals the token but not the private key, they cannot create a valid DPoP proof with the matching thumbprint.

```typescript
import { jwtVerify } from "jose";

async function validateTokenAndDPoP(
  authorization: string, // "DPoP <token>"
  dpopHeader: string,
  method: string,
  uri: string,
) {
  const [scheme, token] = authorization.split(" ");
  if (scheme !== "DPoP" || !token) {
    throw new Error("DPoP-bound tokens must use the DPoP authorization scheme");
  }

  // Validate the access token (a JWT here; opaque tokens need introspection)
  const { payload: tokenPayload } = await jwtVerify(token, jwks);

  // Full proof validation, including ath against this token
  const { thumbprint } = await validateDPopProof(dpopHeader, method, uri, token);

  const cnf = tokenPayload.cnf as { jkt?: string } | undefined;
  if (thumbprint !== cnf?.jkt) {
    throw new Error("DPoP thumbprint does not match token");
  }

  return tokenPayload;
}
```

## When to Require DPoP

DPoP has overhead: every request requires generating and validating a proof. Use it when token compromise is a serious risk:

- **Agent-to-agent communication** where tokens flow through multiple systems
- **Financial operations** (payments, refunds, transfers)
- **User data access** (PII, medical records)
- **Administrative operations** (user creation, permission changes)

For read-only operations on public data, the overhead may not be justified.

## MCP and DPoP

DPoP is not part of the ratified MCP specification. The current `2026-07-28` revision's authorization and security-considerations pages make no mention of it. A DPoP profile for MCP exists only as an open, unmerged proposal ([SEP-1932](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/1932)) - do not describe DPoP as an MCP requirement or recommendation until that lands.

None of this stops an MCP server from adopting DPoP on its own: DPoP is an OAuth-layer mechanism, and an MCP server is still an OAuth resource server underneath. A server that wants sender-constrained tokens for sensitive operations can require DPoP proofs independent of anything MCP-specific:

```typescript
// MCP server validating DPoP
server.setRequestHandler(
  {
    schema: jsonrpc.JsonRpcRequestSchema,
  },
  async (request) => {
    const dpopHeader = request.headers?.["DPoP"] as string;
    const authHeader = request.headers?.["Authorization"] as string;

    if (!dpopHeader) {
      throw new Error("DPoP proof required");
    }

    await validateTokenAndDPoP(authHeader, dpopHeader, request.method, request.uri);
    // ... proceed with request
  },
);
```

See [Protected Resource Metadata](/docs/authentication/protected-resource-metadata) for advertising DPoP requirements.

<Callout type="info">
  Two `2026-07-28` MCP changes are not DPoP-specific, but they make a server-side DPoP
  implementation easier to reason about if you add one. Sessions are removed, so there is no
  connect-time authentication step whose proof a later request could ride on - every request already
  carries its own token, which is the same per-request model DPoP proofs assume. And client
  credentials must now be keyed by issuing authorization server (SEP-2352), so it is unambiguous
  which issuer minted a given DPoP-bound token. The `cnf.jkt` thumbprint itself always binds the
  token to the client's DPoP public key, not to the issuer's signing keys.
</Callout>

## Checklist

- [ ] Clients generate Ed25519 or ES256 keypairs at startup
- [ ] Every request sends `Authorization: DPoP <token>` and a unique proof with `jti`, `htm`, `htu`, `iat`, `ath`
- [ ] Server validates DPoP `typ`, signature, claims, `ath`, and JTI uniqueness
- [ ] Access tokens include a `cnf.jkt` claim with the proof's JWK thumbprint
- [ ] Server validates that DPoP thumbprint matches token claim
- [ ] JTI store prevents reuse (Redis or equivalent for distributed systems)
- [ ] DPoP is required for sensitive operations (financial, user data, admin)
