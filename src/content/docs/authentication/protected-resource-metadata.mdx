## Summary

Publish your resource server's metadata at `/.well-known/oauth-protected-resource` so that MCP clients, agents, and external services can discover your authorization requirements at runtime. Clients use this metadata to find the authorization servers that issue tokens for you and learn which scopes you support. RFC 9728 also defines standard fields for advertising a DPoP requirement.

- `resource`: your API or MCP server's resource URI
- `authorization_servers`: list of trusted identity providers
- `scopes_supported`: all scopes your API recognizes
- `bearer_methods_supported`: accepted bearer token transport methods
- `dpop_bound_access_tokens_required` and `dpop_signing_alg_values_supported`: whether you require DPoP, and which proof algorithms you accept
- Cache with `Cache-Control: max-age=3600`

When an MCP client, external agent, or service needs to call your API, it must know: which authorization servers to trust, which scopes you support, and whether tokens must be sender-constrained. RFC 8414 OAuth 2.0 Authorization Server Metadata defines the authorization server metadata endpoint. RFC 9728 Protected Resource Metadata defines the metadata that a resource server exposes about itself.

Publish this metadata at `/.well-known/oauth-protected-resource` to allow clients (including MCP) to discover your auth requirements and validate tokens correctly.

## Metadata Document Structure

```json
{
  "resource": "https://api.example.com",
  "authorization_servers": ["https://auth.example.com/"],
  "scopes_supported": [
    "invoices:read",
    "invoices:write",
    "customers:read",
    "customers:write",
    "payments:read",
    "payments:write"
  ],
  "bearer_methods_supported": ["header"],
  "dpop_bound_access_tokens_required": false,
  "dpop_signing_alg_values_supported": ["ES256", "EdDSA"],
  "resource_name": "Example API"
}
```

Key fields:

- `resource` - your API's base URI or MCP endpoint resource identifier
- `authorization_servers` - list of auth servers that can issue tokens you accept
- `scopes_supported` - all scopes your API recognizes
- `bearer_methods_supported` - accepted bearer token locations, usually `["header"]`
- `dpop_bound_access_tokens_required` - `true` if every access token must be DPoP-bound (defaults to `false` when omitted)
- `dpop_signing_alg_values_supported` - DPoP proof algorithms the resource accepts
- `resource_name` - human-readable resource name for client UI
- `jwks_uri` (optional, not shown) - the resource server's own public keys, for example for signed responses. It is not where clients or the resource find the keys that verify access tokens; those come from the authorization server's own metadata (RFC 8414 `jwks_uri`) or token introspection

Authorization-server capabilities such as `grant_types_supported`, `response_types_supported`, token endpoints, and token endpoint auth methods belong in the authorization server metadata document, not the protected resource metadata document.

## Agent Registration Discovery

If your service supports agentic user registration through `auth.md`, keep the split explicit:

- Protected-resource metadata tells the agent which resource it is calling and which authorization servers protect it.
- Authorization server metadata advertises the optional `agent_auth` block with identity, claim, and provider-event endpoints. Token revocation remains a top-level OAuth endpoint.
- `auth.md` gives agents a readable walkthrough of the same flow, including supported registration methods, scopes, error recovery, and contact links.

A protected resource can point agents toward the registration path without embedding registration details directly:

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer resource_metadata="https://api.example.com/.well-known/oauth-protected-resource"
```

The authorization server metadata then advertises supported agent registration flows through its optional `agent_auth` block - see [auth.md](/docs/authentication/auth-md) for the full field-by-field example and the current registration model. Treat this metadata as discovery only; authorization still depends on validating the issued bearer token on every request.

## Next.js Implementation

```typescript
// app/.well-known/oauth-protected-resource/route.ts
import { NextResponse } from "next/server";

export async function GET() {
  const metadata = {
    resource: "https://api.example.com",
    authorization_servers: ["https://auth.example.com/"],
    scopes_supported: [
      "invoices:read",
      "invoices:write",
      "customers:read",
      "customers:write",
      "payments:read",
      "payments:write",
    ],
    bearer_methods_supported: ["header"],
    dpop_bound_access_tokens_required: false,
    dpop_signing_alg_values_supported: ["ES256", "EdDSA"],
    resource_name: "Example API",
  };

  return NextResponse.json(metadata, {
    headers: { "Cache-Control": "public, max-age=3600" },
  });
}
```

Serve it at `https://api.example.com/.well-known/oauth-protected-resource`. If the resource identifier has a path, RFC 9728 inserts the well-known segment before it: `https://api.example.com/.well-known/oauth-protected-resource/mcp` for a resource of `https://api.example.com/mcp`. Any other location (such as a `.json` suffix) is a custom endpoint that clients only find if you link it explicitly, for example from `WWW-Authenticate`.

## How MCP Uses This

MCP servers have been required to publish this metadata since the `2025-06-18` revision. MCP clients fetch it to:

1. Discover which authorization servers can issue tokens
2. Learn which scopes the API supports
3. Find each authorization server's own metadata (RFC 8414), which carries its token endpoint and signing keys

DPoP is not part of this discovery flow in the ratified MCP spec - see [DPoP](/docs/authentication/dpop) for why. If your resource server independently requires DPoP (an OAuth-layer decision, not an MCP one), advertise it with RFC 9728's standard `dpop_bound_access_tokens_required` and `dpop_signing_alg_values_supported` fields rather than a private one.

When a client calls your resource server, it:

1. Fetches `/.well-known/oauth-protected-resource`
2. Validates that the `resource` value matches the URL it is calling
3. Fetches the listed authorization server's metadata and obtains a token for that resource
4. Includes a DPoP proof only if `dpop_bound_access_tokens_required` is `true` (or the token is DPoP-bound)

The resource server, not the client, validates each token: signature against the authorization server's keys (or introspection for opaque tokens), plus `iss` and `aud`.

```typescript
// MCP client example (simplified)
async function callResourceServer(token: string, endpoint: string) {
  // Fetch metadata
  const metadata = await fetch("https://api.example.com/.well-known/oauth-protected-resource").then(
    (r) => r.json(),
  );

  // If this resource requires sender-constrained tokens, send a DPoP proof
  const headers: Record<string, string> = {};
  if (metadata.dpop_bound_access_tokens_required) {
    headers.Authorization = `DPoP ${token}`;
    headers.DPoP = await generateDPopProof("GET", endpoint, token);
  } else {
    headers.Authorization = `Bearer ${token}`;
  }

  const res = await fetch(endpoint, { headers });
  return res.json();
}
```

<Callout type="info">
  Current `2026-07-28` behavior: the metadata document itself is unchanged, but two client
  obligations around it tighten. Clients must validate the `iss` parameter on the authorization
  response against the issuer they discovered through this document, per RFC 9207 (SEP-2468), and
  must store client credentials keyed by that issuer rather than by resource, re-registering when a
  resource's `authorization_servers` entry changes (SEP-2352). A stable, correct `issuer` in your
  authorization server metadata matters more than before: changing it invalidates every client
  credential registered against it.
</Callout>

## Minimal Metadata for Simple APIs

If you're not using DPoP or token exchange yet, a minimal metadata document is acceptable:

```json
{
  "resource": "https://api.example.com",
  "authorization_servers": ["https://auth.example.com/"],
  "scopes_supported": ["read", "write"],
  "bearer_methods_supported": ["header"]
}
```

## Publishing Metadata in OpenAPI

You can reference protected resource metadata in your OpenAPI spec:

```yaml
openapi: 3.1.0
info:
  title: Example API
  version: 1.0.0
servers:
  - url: https://api.example.com
components:
  securitySchemes:
    oauth2:
      type: oauth2
      flows:
        clientCredentials:
          tokenUrl: https://auth.example.com/token
          scopes:
            invoices:read: Read invoices
            invoices:write: Create and update invoices
paths:
  /invoices:
    get:
      security:
        - oauth2: [invoices:read]
      responses:
        "200":
          description: List of invoices

x-oauth-protected-resource: /.well-known/oauth-protected-resource
```

`x-oauth-protected-resource` is a custom extension, not part of OpenAPI or RFC 9728. It helps tooling you control or document; don't expect general OpenAPI tools to act on it.

## Cache and Update Strategy

The metadata document is relatively stable but can change when you:

- Add new scopes
- Support DPoP
- Add token exchange support
- Change authorization servers

Clients typically cache metadata for 1 hour (specify `Cache-Control: max-age=3600`). When you make changes, the cache expires naturally. For immediate propagation, rotate the URI or notify clients.

## Checklist

- [ ] Endpoint is served at `/.well-known/oauth-protected-resource`
- [ ] `resource` matches your API's base URI or MCP endpoint resource identifier
- [ ] `authorization_servers` includes all trusted identity providers
- [ ] `scopes_supported` is exhaustive and matches your API's permission model
- [ ] DPoP requirements, if any, use `dpop_bound_access_tokens_required` and `dpop_signing_alg_values_supported`
- [ ] Token-verification keys are published in the authorization server's metadata, not assumed from this document
- [ ] `bearer_methods_supported` is explicit and does not permit query-string bearer tokens
- [ ] Authorization server metadata advertises the grants and token endpoint methods clients can use
- [ ] Response includes `Cache-Control` header with appropriate TTL
- [ ] Metadata is served with `Content-Type: application/json`
