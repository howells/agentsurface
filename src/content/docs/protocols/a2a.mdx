## Summary

A2A is horizontal (agent-to-agent) vs. MCP which is vertical (agent-to-tools). One agent discovers a peer's capabilities via AgentCard at `/.well-known/agent-card.json`, hands off a task with context, and receives results asynchronously. Works across organizational boundaries without pre-shared secrets. Spec: v1.0.1 (2026-05-28; v1.0.0 shipped 2026-03-12). Donated to the Linux Foundation 2025-06-23; [accepted as a Growth Stage project at the Agentic AI Foundation (AAIF)](https://a2a-protocol.org/latest/blog/2026/08/27/a-new-chapter-for-a2a-joining-the-agentic-ai-foundation/) on 2026-08-27.

```
Orchestrator        Specialist
   (Agent A)        (Agent B)
     ├─ GET /.well-known/agent-card.json
     │  (discover capabilities)
     ├─ SendMessage (hand off task)
     └─ Poll, stream, or callback for result
```

- AgentCard: the server agent publishes its name, interfaces, capabilities, skills, and security requirements at a well-known location
- Task-based: async, long-lived, with streaming/callback progress
- Authentication is declared in the card (API key, HTTP auth, OAuth 2.0, OpenID Connect, or mutual TLS); Agent Cards can carry JWS signatures
- Works across org boundaries, different infrastructure
- Multi-transport: JSON-RPC, gRPC, and HTTP+JSON
- v1.0.1: production-grade - 150+ organizations, SDKs in 5 languages, an 8-state task lifecycle

A2A solves a different problem than MCP. Where MCP connects an agent to tools and data sources, A2A connects agents to other agents. It defines how one agent discovers a peer agent's capabilities, hands off a task with full context, and receives results back - across organizational and deployment boundaries.

## Origin and Governance

Google initially developed and published the A2A specification in April 2025 as an open-source protocol for multi-agent coordination. It was donated to the Linux Foundation on 2025-06-23, and was accepted as a **Growth Stage project** at the Agentic AI Foundation (AAIF) - alongside MCP - on 2026-08-27, making A2A a vendor-neutral standard. The spec reached v1.0.0 on 2026-03-12 and v1.0.1 on 2026-05-28 - production-grade, with 150+ participating organizations and SDKs across five languages. For current adopters and governance details, use the A2A project site rather than copying a vendor list into implementation docs.

IBM's separate "ACP" (Agent Communication Protocol) was absorbed into A2A in August 2025 and is no longer a separate effort. See [Checkout Protocols](/docs/agentic-commerce/checkout-protocols) for the three unrelated protocols that share that acronym.

## Purpose

In a multi-agent system, not every agent can or should do everything. A travel booking agent does not need to understand flight pricing algorithms - it needs to hand that task to a specialist flight agent. A customer support orchestrator should not contain HR policy logic - it should delegate HR questions to an HR specialist agent.

A2A defines how that delegation works in practice:

- How the orchestrator discovers that a specialist exists and what it handles
- How to hand off the task with sufficient context
- How to receive results, ask clarifying questions, and complete the workflow

The key design constraint is that A2A works across organizational boundaries. The orchestrating agent and the specialist may be deployed by different organizations, with different authentication systems, running on different infrastructure.

## Relationship to MCP

MCP is vertical: an agent connects downward to tools and data sources.
A2A is horizontal: an agent connects across to peer agents.

```
                    ┌─────────────────────┐
                    │  Orchestrator Agent  │
                    └────────┬────────────┘
                             │
              A2A (horizontal delegation)
           ┌─────────────────┴──────────────────┐
           │                                    │
  ┌────────▼────────┐                  ┌────────▼────────┐
  │  Flight Agent   │                  │  Hotel Agent    │
  └────────┬────────┘                  └────────┬────────┘
           │                                    │
     MCP (vertical)                       MCP (vertical)
  ┌────────▼────────┐                  ┌────────▼────────┐
  │  Flight APIs    │                  │  Hotel APIs     │
  │  Pricing DB     │                  │  Availability   │
  └─────────────────┘                  └─────────────────┘
```

A common architecture uses both protocols: agents use MCP to access their own tools and A2A to delegate tasks to peer agents.

## Task Lifecycle

### Phase 1: Discovery

Before an agent can delegate a task, it must find an agent that can handle it and verify its capabilities. A2A uses AgentCard for discovery - a JSON document published at a well-known URL on the target agent's domain.

The canonical location is:

```
GET /.well-known/agent-card.json
```

Pre-1.0 agents published `.well-known/agent.json`. Some clients probe that path as an optional compatibility step, but the specification's path is `agent-card.json`, so do not rely on a server answering at the old one.

A client agent fetches this document to learn:

- What tasks the agent handles
- What authentication it requires
- What endpoints to call
- What input and output formats it supports

### Phase 2: Authorization

Once the client has read the Agent Card and confirmed the specialist can handle the task, it establishes authorization. A2A does not mandate one scheme: the Agent Card declares what it accepts in `securitySchemes` (API key, HTTP authentication, OAuth 2.0, OpenID Connect, or mutual TLS) and which of them a caller must satisfy in `securityRequirements`. When the card declares OAuth, the client obtains a token scoped to that agent using the flows and scopes in the card.

### Phase 3: Communication

With a valid token, the client sends task requests to the specialist over an interface the card lists in `supportedInterfaces` (JSON-RPC, gRPC, or HTTP+JSON). Responses arrive either synchronously or as a stream of updates for long-running tasks.

## AgentCard Structure

The AgentCard is the core discovery document. Every A2A-compatible agent publishes one at `/.well-known/agent-card.json`.

```json
{
  "name": "ACME Flight Specialist",
  "description": "Searches, compares, and books commercial flights. Handles multi-leg itineraries, fare class selection, and seat assignments.",
  "version": "2.3.1",
  "supportedInterfaces": [
    {
      "url": "https://agents.acme.com/flight",
      "protocolBinding": "JSONRPC",
      "protocolVersion": "1.0"
    }
  ],
  "capabilities": {
    "streaming": true,
    "pushNotifications": false
  },
  "securitySchemes": {
    "acmeOAuth": {
      "oauth2SecurityScheme": {
        "flows": {
          "authorizationCode": {
            "authorizationUrl": "https://auth.acme.com/oauth/authorize",
            "tokenUrl": "https://auth.acme.com/oauth/token",
            "pkceRequired": true,
            "scopes": {
              "flight:search": "Search flights without booking",
              "flight:book": "Search and book flights on behalf of users"
            }
          }
        }
      }
    }
  },
  "securityRequirements": [{ "schemes": { "acmeOAuth": { "list": ["flight:search"] } } }],
  "defaultInputModes": ["text/plain", "application/json"],
  "defaultOutputModes": ["application/json"],
  "skills": [
    {
      "id": "flight-search",
      "name": "Search Flights",
      "description": "Find available flights between two airports for given dates and passenger count. Returns ranked options with pricing.",
      "tags": ["flights", "travel", "search"],
      "inputModes": ["application/json"],
      "outputModes": ["application/json"],
      "examples": ["Find business class flights from JFK to LHR for 2 passengers on March 15"]
    },
    {
      "id": "flight-book",
      "name": "Book Flight",
      "description": "Book a specific flight from search results. Requires passenger details and payment authorization.",
      "tags": ["flights", "travel", "booking"],
      "inputModes": ["application/json"],
      "outputModes": ["application/json"]
    }
  ]
}
```

### AgentCard Fields

| Field                  | Required | Description                                                                  |
| ---------------------- | -------- | ---------------------------------------------------------------------------- |
| `name`                 | Yes      | Human-readable display name                                                  |
| `description`          | Yes      | What tasks this agent handles - the primary discovery signal                 |
| `version`              | Yes      | Version of this agent                                                        |
| `supportedInterfaces`  | Yes      | Ordered endpoints, each with `url`, `protocolBinding`, and `protocolVersion` |
| `capabilities`         | Yes      | Which A2A features this agent supports                                       |
| `skills`               | Yes      | Array of specific tasks this agent can perform                               |
| `defaultInputModes`    | Yes      | MIME types this agent accepts by default                                     |
| `defaultOutputModes`   | Yes      | MIME types this agent produces by default                                    |
| `securitySchemes`      | No       | Named auth scheme definitions, including OAuth 2.0 flows                     |
| `securityRequirements` | No       | Which declared scheme and scopes a caller must use                           |
| `signatures`           | No       | JWS signatures over the card                                                 |

The card has no top-level `id` or `url`; the endpoint lives in `supportedInterfaces`. Authentication fields are conditional on the schemes you advertise.

### Capabilities Declaration

```json
{
  "capabilities": {
    "streaming": true,
    "pushNotifications": false,
    "extendedAgentCard": false
  }
}
```

| Capability          | Meaning                                                 |
| ------------------- | ------------------------------------------------------- |
| `streaming`         | Agent supports streaming updates for long-running tasks |
| `pushNotifications` | Agent can send async push updates via webhook           |
| `extensions`        | Protocol extensions the agent supports, by URI          |
| `extendedAgentCard` | Agent serves a fuller card to authenticated callers     |

Older cards listed `stateTransitionHistory`; it is not a 1.0 capability.

## Task Communication & Security

A2A authentication is whatever the target card declares. A client must satisfy one of the card's `securityRequirements` before sending tasks, and agents should scope credentials to the skills they expose. A2A does not require DPoP (RFC 9449); use sender-constrained tokens only if the authorization server you choose offers them. The examples below are JSON-RPC binding examples against the v1.0 schema; the other bindings carry the same messages.

### Sending a Task

Task requests are JSON-RPC calls to the agent's endpoint. The task ID is assigned by the agent in its response; the request carries a client-generated `messageId`:

```json
POST https://agents.acme.com/flight
Authorization: Bearer eyJ...
A2A-Version: 1.0
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": "req-8821",
  "method": "SendMessage",
  "params": {
    "message": {
      "messageId": "msg-0001",
      "role": "ROLE_USER",
      "parts": [
        {
          "text": "Find available business class flights from JFK to LHR on March 15, 2026 for 2 passengers."
        }
      ]
    },
    "metadata": {
      "originAgent": "agent:acme-travel/orchestrator",
      "correlationId": "trip-planning-session-4421"
    }
  }
}
```

### Task States

A task moves through a defined set of states. v1.0.1 specifies eight operational states (the schema also defines `TASK_STATE_UNSPECIFIED`). On the wire they are ProtoJSON enum values such as `TASK_STATE_WORKING`; the table uses short names:

```
submitted → working → (input-required / auth-required →) completed
                    ↘ failed
                    ↘ canceled
                    ↘ rejected
```

| State            | Meaning                                                |
| ---------------- | ------------------------------------------------------ |
| `submitted`      | Task received, queued for processing                   |
| `working`        | Agent is actively processing                           |
| `input-required` | Agent needs additional information before continuing   |
| `auth-required`  | Agent needs additional authorization before continuing |
| `completed`      | Task finished successfully                             |
| `failed`         | Task failed with an error                              |
| `canceled`       | Task was canceled before completion                    |
| `rejected`       | Agent declined the task before starting work           |

### Streaming Responses

For long-running tasks, a client calls `SendStreamingMessage` (the card must declare `capabilities.streaming`) and the agent streams updates via Server-Sent Events. Each event is a `StreamResponse` that wraps exactly one of `task`, `message`, `statusUpdate`, or `artifactUpdate`:

```
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache

data: {"jsonrpc":"2.0","id":"req-8821","result":{"task":{"id":"task-8821","contextId":"ctx-4421","status":{"state":"TASK_STATE_SUBMITTED"}}}}

data: {"jsonrpc":"2.0","id":"req-8821","result":{"statusUpdate":{"taskId":"task-8821","contextId":"ctx-4421","status":{"state":"TASK_STATE_WORKING"}}}}

data: {"jsonrpc":"2.0","id":"req-8821","result":{"artifactUpdate":{"taskId":"task-8821","contextId":"ctx-4421","artifact":{"artifactId":"flights-1","parts":[{"data":{"flights":[]},"mediaType":"application/json"}]},"lastChunk":true}}}

data: {"jsonrpc":"2.0","id":"req-8821","result":{"statusUpdate":{"taskId":"task-8821","contextId":"ctx-4421","status":{"state":"TASK_STATE_COMPLETED"}}}}
```

The stream ends when the task reaches a terminal state (`completed`, `failed`, `canceled`, or `rejected`). A part holds exactly one of `text`, `raw`, `url`, or `data`, with an optional `mediaType`.

### Input Required

When an agent needs more information mid-task, it moves the task to `TASK_STATE_INPUT_REQUIRED` and puts the question in the status message:

```json
{
  "jsonrpc": "2.0",
  "id": "req-8821",
  "result": {
    "task": {
      "id": "task-8821",
      "contextId": "ctx-4421",
      "status": {
        "state": "TASK_STATE_INPUT_REQUIRED",
        "message": {
          "messageId": "msg-0002",
          "role": "ROLE_AGENT",
          "parts": [
            {
              "text": "Found 12 flights matching your criteria. Do you prefer morning departures (before noon) or afternoon departures (after noon)?"
            }
          ]
        }
      }
    }
  }
}
```

The orchestrator replies with a new message that names the same task in `message.taskId`:

```json
{
  "jsonrpc": "2.0",
  "id": "req-8822",
  "method": "SendMessage",
  "params": {
    "message": {
      "messageId": "msg-0003",
      "taskId": "task-8821",
      "role": "ROLE_USER",
      "parts": [{ "text": "Morning departures preferred." }]
    }
  }
}
```

## When to Use A2A

Use A2A when the work itself should be done by a separate agent that owns the domain knowledge and tooling:

- **Cross-organizational delegation** - sending a task to an agent operated by a different organization
- **Specialist routing** - an orchestrator directing tasks to domain-specific agents (legal, HR, finance)
- **Parallel execution** - dispatching independent subtasks to multiple agents simultaneously and aggregating results
- **Long-running workflows** - tasks that take minutes or hours, where the result is delivered asynchronously

Do not use A2A when you just need to call a function or read data. That is what MCP tools and resources are for.

```
Orchestrator needs to:

  Call an API endpoint?            → MCP tool
  Read a file or document?         → MCP resource
  Ask a specialist to handle it?   → A2A task delegation
  Complete a multi-step commerce?  → ACP
```

## Skills Catalogue

The `skills` array in an AgentCard describes discrete capabilities the agent exposes. Unlike MCP tools (which are atomic functions), A2A skills represent multi-step tasks that may involve reasoning, user interaction, or cross-organizational workflows. Examples help orchestrators match natural-language tasks to the right skill.
